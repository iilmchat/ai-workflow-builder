## 0. Как пользоваться этим документом

1. **Кейсы идут блоками** (AUTH, CANVAS, ENGINE, LLM/MEDIA, VECTOR/AGENT,
   SHARE/ACCESS, STORAGE, EDGE, CONTRACT, V0.10). Внутри блока — сквозная
   нумерация, например `CANVAS-07` или `DOCKER-01`.
2. **У каждого кейса есть:** название, приоритет, предусловие, шаги, ожидаемый
   результат. Если шаг требует данных — они указаны в предусловии или прямо в шаге.
3. **Приоритеты:**
   - **P1** — блокирующий: без него релиз не выпускается;
   - **P2** — важный: выпуск возможен с записью в KI;
   - **P3** — косметика/редкий сценарий.
4. **Результат фиксируется** коротко: `PASS` / `FAIL` + путь к скриншоту или
   JSON-файлу. Для FAIL — баг-репорт по шаблону из § 14 и ссылка на KI.
5. **Правило «до/после» (RULES 4.33).** Для проверок вида «закрылось /
   не открылось / не изменилось» сначала зафиксируйте состояние **до**
   действия, иначе «после» неотличимо от исходного.
6. **Не тестируйте по памяти.** Ожидаемые значения (лимиты, сообщения, поля
   API) сверяйте с кодом и контрактами, ссылки на них есть в каждом блоке.

**Тестовые сценарии**, которые понадобятся:

1. `QA-BASE` — `Текст → LLM → Вывод` (быстрый старт).
2. `QA-FAIL` — `Текст → LLM` с заведомо недоступной моделью (для проверки
   блокировки запуска).
3. `QA-RAG` — `Текст → Запись в вектор` и `Текст → Векторный поиск → LLM`.
4. `QA-AGENT` — `Текст → Агент (HTTP-запрос) → Вывод`.
5. `QA-MEDIA` — `Текст → Генерация изображения → Медиа-инструмент (Апскейл)`.
6. `QA-BIG` — 40–50 узлов, разброс координат ~20 000 px (для Fit/миникарты).
7. `QA-SEARCH` — `Текст → Веб-поиск → LLM → Вывод`.
8. `QA-DOCS` — `Текст (Markdown) → Генерация документа → Вывод` и вариант с JSON.
9. `QA-FILES` — `Запись файла → Чтение файла` (два запуска) и `Чтение файла → LLM`.

## 2. AUTH — аутентификация

**Что проверяем по контракту:** `POST /auth/register`, `/auth/login`,
`/auth/refresh`, `/auth/logout`, `GET /auth/me`; access-токен живёт **только в
памяти** (R6.1b.2), refresh — httpOnly-cookie; лимит `POST /auth/login` —
5 попыток в минуту с IP.

#### AUTH-01 — Регистрация нового пользователя
**Приоритет:** P1 · **Тип:** smoke
**Предусловие:** backend и БД доступны, `AUTH_DISABLED=false`; email
`qa-a+<таймстамп>@example.com` ещё не зарегистрирован.
**Шаги:**
1. Открыть `http://127.0.0.1:5173/login`.
2. Нажать «Нет аккаунта? Зарегистрироваться».
3. Ввести email и пароль из 8 символов.
4. Нажать «Зарегистрироваться».
**Ожидаемый результат:**
- Редирект на `/`, открывается холст, в шапке виден email пользователя.
- `POST /auth/register` → 2xx; в ответе есть `accessToken` и `user`.
- Refresh-cookie выставлена (`HttpOnly`, `SameSite`), access-токен в ответе.
- В шапке отображается строка копирайта с версией (`[data-app-version]`), и она
  совпадает с `version` из `web/package.json` (на момент релиза — `0.10.0`,
  KI-446).

#### AUTH-02 — Регистрация на существующий email
**Приоритет:** P1
**Предусловие:** `QA-A` уже зарегистрирован, пользователь разлогинен.
**Шаги:**
1. Открыть `/login`, переключиться на «Зарегистрироваться».
2. Ввести email `QA-A` и любой валидный пароль.
3. Отправить форму.
**Ожидаемый результат:**
- Под формой — «Этот email уже зарегистрирован».
- Пользователь остаётся на `/login`, сессии нет.
- Backend отвечает ошибкой (409/400), в логах нет стектрейса в ответе.

#### AUTH-03 — Вход с валидными данными
**Приоритет:** P1 · **Тип:** smoke
**Предусловие:** `QA-A` существует, `AUTH_DISABLED=false`.
**Шаги:**
1. Открыть `/login` (режим «Войти»).
2. Ввести email/пароль `QA-A`.
3. Нажать «Войти».
**Ожидаемый результат:**
- Редирект на `/`; имя сценария — «Новый workflow»; холст пустой.
- `POST /auth/login` → 2xx; `GET /auth/me` c `Authorization: Bearer …` → 200.
- В шапке доступны «Сохранить» и «Запустить» (пользователь не viewer).

#### AUTH-04 — Вход с неверным паролем
**Приоритет:** P1
**Предусловие:** `QA-A` существует.
**Шаги:**
1. Открыть `/login`.
2. Ввести корректный email и неверный пароль.
3. Нажать «Войти».
**Ожидаемый результат:**
- Сообщение «Неверный email или пароль».
- Пользователь остаётся на `/login`, токен не выдан.
- Счётчик лимита попыток увеличился (см. AUTH-10).

#### AUTH-05 — Валидация email на форме
**Приоритет:** P2
**Предусловие:** открыта форма входа.
**Шаги:**
1. Ввести `not-an-email` в поле email.
2. Ввести пароль из 8 символов.
3. Нажать «Войти».
**Ожидаемый результат:**
- Сообщение «Введите корректный email».
- Запрос на backend **не уходит** (проверить в Network).

#### AUTH-06 — Границы длины пароля
**Приоритет:** P2
**Предусловие:** открыта форма регистрации, email уникален.
**Шаги:**
1. Ввести пароль из 7 символов → отправить.
2. Ввести пароль из 73 символов → отправить.
3. Ввести пароль из 8 символов → отправить.
**Ожидаемый результат:**
- Шаги 1–2: «Пароль должен быть от 8 до 72 символов», запроса нет.
- Шаг 3: регистрация успешна (или ошибка «email занят», если повторно).

#### AUTH-07 — Защита маршрута и сохранение deep-link
**Приоритет:** P1
**Предусловие:** пользователь разлогинен; существует сценарий с id `W`
(`QA-A`).
**Шаги:**
1. Открыть `/` без сессии.
2. Открыть `/login` напрямую в новой вкладке.
3. Открыть `/` c параметром `?workflowId=W` без сессии, затем войти.
**Ожидаемый результат:**
- Шаг 1: редирект на `/login`.
- Шаг 2: `ProtectedRoute` не пускает на холст.
- Шаг 3: после логина открывается **тот же** `?workflowId=W`, сценарий
  загружается (тост «Workflow загружен: …»).

#### AUTH-08 — Восстановление сессии после F5
**Приоритет:** P1 · **Тип:** smoke
**Предусловие:** выполнен вход `QA-A`; открыт сценарий.
**Шаги:**
1. Нажать F5.
2. Дождаться загрузки.
**Ожидаемый результат:**
- Холст восстанавливается, сценарий тот же, пользователь остаётся в системе.
- В Network виден `POST /auth/refresh` (2xx) — сессия поднята по cookie.
- В `localStorage`/`sessionStorage` **нет** access-токена (см. AUTH-11).

#### AUTH-09 — Выход из аккаунта
**Приоритет:** P1
**Предусловие:** выполнен вход.
**Шаги:**
1. Нажать на кнопку профиля (`[data-user-menu]`).
2. Нажать «Выйти».
3. Нажать F5.
4. Открыть `/` напрямую.
**Ожидаемый результат:**
- Редирект на `/login`.
- `POST /auth/logout` → 2xx, refresh-cookie очищена, токен отозван.
- Шаги 3–4: сессия не восстанавливается, снова `/login`.

#### AUTH-10 — Лимит попыток входа (brute-force)
**Приоритет:** P2
**Предусловие:** `AUTH_DISABLED=false`; окно лимита — 60 секунд.
**Шаги:**
1. Выполнить 5 попыток входа с неверным паролем.
2. Выполнить шестую попытку в течение той же минуты.
**Ожидаемый результат:**
- 5 попыток: обычная ошибка «Неверный email или пароль».
- 6-я: HTTP 429 (UI показывает ошибку, приложение не зависает).
- Через минуту вход с верным паролем снова работает.

#### AUTH-11 — Access-токен не попадает в Web Storage
**Приоритет:** P1 · **Тип:** security
**Предусловие:** выполнен вход.
**Шаги:**
1. Открыть DevTools → Application → Local Storage и Session Storage.
2. Найти любые значения, похожие на JWT (`eyJ…`).
3. Проверить cookie: refresh-токен должен быть `HttpOnly`.
**Ожидаемый результат:**
- В Web Storage **нет** access-токена (допустимы только `theme`, `lang`).
- Access-токен доступен только в памяти вкладки.
- Refresh-cookie помечена `HttpOnly` (не читается из JS).

#### AUTH-12 — `AUTH_DISABLED=true` (dev-режим)
**Приоритет:** P2
**Предусловие:** `.env` c `AUTH_DISABLED=true`, backend перезапущен; `NODE_ENV`
= `development`.
**Шаги:**
1. Открыть `/` без логина.
2. Выполнить сценарий: сохранить и запустить.
3. Попробовать переключить `NODE_ENV=production` при `AUTH_DISABLED=true` и
   перезапустить backend.
**Ожидаемый результат:**
- Шаги 1–2: холст доступен без формы входа, сценарии сохраняются.
- Шаг 3: приложение **не стартует**, в логах ошибка конфигурации
  («`AUTH_DISABLED=true` недопустим в production»).

## 3. CANVAS UI — холст

**Что проверяем:** добавление узлов, каталог, связи, удаление, режимы,
хоткеи, миникарта, комментарии, автосохранение, загрузка/экспорт/импорт,
deep-link. Все ID-узлов из реестра: `text`, `llm`, `image_generation`,
`image_tool`, `video_generation`, `audio_generation`, `music_generation`,
`comment`, `http`, `condition`, `output`, `compare`, `sub_workflow`,
`vector_upsert`, `vector_query`, `memory_read`, `memory_write`, `agent`.

#### CANVAS-01 — Добавление узла кнопкой тулбара
**Приоритет:** P1 · **Тип:** smoke
**Предусловие:** выполнен вход, граф пуст.
**Шаги:**
1. Нажать 📝 «Текст» в нижнем тулбаре.
2. Нажать 🤖 «LLM».
3. Нажать 🖼 «Генерация изображения».
**Ожидаемый результат:**
- Появились три узла с правильными иконками и подписями.
- Узлы не накладываются друг на друга (раскладка сеткой от центра).
- У каждого узла есть шапка, тело и кнопка удаления при наведении.

## 4. ENGINE EXECUTION — выполнение

**Что проверяем:** статусы запуска и узлов, `skipped`, сохранение перед
запуском, ретраи BullMQ, восстановление после F5, SSE-поток, панель результата.
Контракт событий — [`sse-contract.json`](../development/sse-contract.json):
`snapshot`, `run_started`, `node_started`, `node_completed`, `node_failed`,
`node_skipped`, `run_completed`.

#### ENGINE-01 — Успешный запуск линейного графа
**Приоритет:** P1 · **Тип:** smoke
**Предусловие:** сценарий `QA-BASE` (Текст → LLM → Вывод), модель доступна.
**Шаги:**
1. Ввести текст, нажать «Запустить».
2. Наблюдать бейдж, рамки узлов и панель.
3. Кликнуть по узлу LLM.
**Ожидаемый результат:**
- Бейдж: «Создаётся…» → «Выполняется…» → «Готово».
- Рамки: серые → синяя (running) → зелёные (completed).
- В панели у LLM: статус «завершён», раздел «Вывод» с текстом, метрики
  (токены/стоимость/время), логи.
- `GET /runs/:id` → `status=completed`.

#### ENGINE-02 — Падение узла и `skipped` у зависимых
**Приоритет:** P1
**Предусловие:** сценарий из трёх узлов, где средний заведомо падает
(например, HTTP на недоступный адрес).

**Ожидаемый результат:**
- Упавший узел — красный, статус `failed`, в панели текст ошибки.
- Зависимый узел — серый пунктир, подпись «Пропущен: упал предшественник»,
  статус `skipped`; это **не** ошибка запуска.
- Бейдж запуска — «Ошибка».

#### ENGINE-03 — Пустой граф и граф только из комментариев
**Приоритет:** P2
**Предусловие:** холст пуст / только стикеры.
**Шаги:**

**Ожидаемый результат:**

- После перезагрузки граф содержит правки.
- `PATCH /workflow/:id` идёт **до** `POST /runs`.

#### ENGINE-05 — Повторные попытки и бейдж «попытка N/M»
**Приоритет:** P2
**Предусловие:** у job'а запуска `attempts=3` (`src/runs/runs.module.ts`,

**Шаги:**
1. Запустить сценарий.
2. Во время выполнения остановить backend (или уронить воркер), затем поднять.
3. Дождаться завершения.
**Ожидаемый результат:**
- В бейдже видно «(попытка 2/M)» и подсказку «Предыдущая попытка упала —
  BullMQ повторит запуск».
- После успешной попытки статус `completed`, ошибка предыдущей попытки в панели
  не остаётся рядом со статусом «завершён».

**Шаги:**

2. Подождать 10–15 секунд, затем вернуть сеть.
3. Если ошибки продолжаются — дождаться тоста.
**Ожидаемый результат:**
- Клиент повторяет подключение; после возврата сети поток восстанавливается.
- При исчерпании попыток — тост «Поток запуска не отвечает (ошибок подряд: N)».
- UI не зависает на «Выполняется…» навсегда.

#### ENGINE-08 — Панель результата: разделы и свёртывание

**Предусловие:** завершённый запуск с ошибкой и успехом.

**Ожидаемый результат:**

- Упавший: «Ошибка» с текстом причины, «Логи» с ретраями.
- Свёрнутая панель оставляет заголовок; холст перерисовывается без артефактов.
- Клик по пустому месту возвращает панель к итогу запуска.

#### ENGINE-09 — Параллельные ветки
**Приоритет:** P2
**Предусловие:** граф «Текст → LLM-A» и «Текст → LLM-B» (две независимые
ветки от одного узла).
**Шаги:**

**Ожидаемый результат:**

#### ENGINE-10 — Блокировка запуска при недоступной модели
**Приоритет:** P1

## 8. S3 / STORAGE

**Что проверяем:** `MEDIA_STORAGE_BACKEND=local|s3|none`, поля
`node_runs.stored_url`/`stored_expires_at`, отдачу `/media/file/:runId/:fileName`,
presigned-ссылки S3, `S3_PUBLIC_BUCKET`, TTL и cleanup, поведение при недоступном
хранилище. Требования — DESIGN § 3.8; KI-443 (переподпись), KI-444
(`publicBucket`).

#### STORAGE-01 — Локальное хранилище (default)
**Приоритет:** P1
**Предусловие:** `MEDIA_STORAGE_BACKEND=local`,
`MEDIA_STORAGE_LOCAL_PATH=./data/media`.
**Шаги:**
1. Запустить сценарий с генерацией изображения.
2. В узле открыть ссылку результата.
3. Проверить файл на диске.
**Ожидаемый результат:**
- В БД `node_runs.stored_url` = `/media/file/<runId>/<file>`.
- Ссылка открывается (200), файл есть в `./data/media/<runId>/`.
- Ссылка провайдера в разметке не используется.

#### STORAGE-02 — S3 / MinIO
**Приоритет:** P1
**Предусловие:** `MEDIA_STORAGE_BACKEND=s3`, MinIO поднят, бакет создан,
`S3_*` заполнены, `S3_PUBLIC_BUCKET=false`.
**Шаги:**
1. Запустить media-сценарий.
2. Открыть `stored_url` в браузере.
3. Проверить в ссылке `X-Amz-Signature`.
**Ожидаемый результат:**
- Файл загружен в бакет (`mc ls` показывает объект).
- `stored_url` — presigned GET, открывается (200), содержит подпись и срок.
- `stored_expires_at` соответствует TTL (`S3_TTL_DAYS`, по умолчанию 30 дней).

#### STORAGE-03 — Истёкший TTL → плашка
**Приоритет:** P1
**Предусловие:** у строки `node_runs` вручную выставить
`stored_expires_at = now() - interval '1 day'`.
**Шаги:**
1. Открыть сценарий с этим запуском.
2. Посмотреть узел.
3. Запустить сценарий заново.
**Ожидаемый результат:**
- В узле плашка «Ссылка истекла — файл больше недоступен».
- Битой картинки/видео нет; в консоли нет 403/404 по медиа.
- Повторный запуск создаёт новую копию и показывает результат.
- Для приватного S3 кейс актуален, если переподпись невозможна (KI-443); при
  работающей переподписи проверяйте STORAGE-05 — плашки быть не должно.

#### STORAGE-04 — Публичный бакет (`S3_PUBLIC_BUCKET=true`)
**Приоритет:** P2
**Предусловие:** `MEDIA_STORAGE_BACKEND=s3`, `S3_PUBLIC_BUCKET=true`, бакет с
публичным чтением; backend перезапущен.
**Шаги:**
1. Запустить media-сценарий.
2. Проверить `stored_url` и открыть его.
**Ожидаемый результат:**
- `stored_url` — прямой URL `<endpoint>/<bucket>/<key>` **без** подписи.
- Ссылка открывается без авторизации.
- Приватный бакет + `publicBucket=true` даёт 403 — это ожидаемо, конфигурация
  неверна.

#### STORAGE-05 — Переподпись presigned-ссылки при чтении
**Приоритет:** P2
**Предусловие:** S3-бакет приватный; у запуска `stored_expires_at` в прошлом, но
файл в бакете есть (KI-443).
**Шаги:**
1. Открыть сценарий (загрузка последнего запуска).
2. Посмотреть ссылку результата.
3. Сравнить с `node_runs.stored_url` в БД.
**Ожидаемый результат:**
- UI получает **свежую** подпись и новый `storedExpiresAt` (проекция в ответе),
  плашка «истекла» не показывается.
- В БД ссылка **не** перезаписывается (снимок — проекция).
- Если переподпись не удалась (S3 недоступен) — показывается плашка, запуск не
  падает; в логах warn.
- Если KI-443 ещё не влит (переподписи нет) — кейс фиксируется как FAIL с
  привязкой к KI-443: ожидание описывает целевое поведение релиза.

#### STORAGE-06 — `MEDIA_STORAGE_BACKEND=none`
**Приоритет:** P2
**Предусловие:** `MEDIA_STORAGE_BACKEND=none`, backend перезапущен.
**Шаги:**
1. Запустить media-сценарий.
2. Открыть узел.
**Ожидаемый результат:**
- `stored_url = null`; ссылка провайдера **не** подставляется в разметку.
- Показывается плашка «Ссылка истекла» (честно: копии у нас нет).
- Запуск успешен, `outputs` содержит провайдерскую ссылку (для совместимости).

#### STORAGE-07 — Недоступное хранилище (S3 down)
**Приоритет:** P2
**Предусловие:** S3/MinIO остановлен, `MEDIA_STORAGE_BACKEND=s3`.
**Шаги:**
1. Запустить media-сценарий.
2. Посмотреть статус узла и логи backend.
**Ожидаемый результат:**
- Узел **не падает** из-за хранилища: результат выполнения сохраняется,
  `stored_url=null`, в UI — плашка.
- В логах — предупреждение об ошибке загрузки без секретов и подписи.
- После поднятия S3 следующий запуск сохраняет файл.

#### STORAGE-08 — Cleanup старых файлов
**Приоритет:** P3
**Предусловие:** `MEDIA_STORAGE_BACKEND=local`,
`MEDIA_STORAGE_LOCAL_TTL_DAYS=1`; есть файлы старше суток.
**Шаги:**
1. Дождаться выполнения job'а очистки (раз в сутки) или запустить его вручную.
2. Проверить каталог и ссылки в БД.
**Ожидаемый результат:**
- Файлы старше TTL удалены с диска.
- Для удалённых файлов UI показывает плашку (ссылка не открывается 404).
- Файлы моложе TTL не тронуты.

#### STORAGE-09 — Доступ к `/media/file/:runId/:fileName`
**Приоритет:** P2
**Предусловие:** есть локальный файл запуска `QA-A`.
**Шаги:**
1. Открыть ссылку своего файла.
2. Подменить `runId` на чужой запуск.
3. Подставить `../` в имя файла (попытка path traversal).
**Ожидаемый результат:**
- Своя ссылка открывается (200) с корректным `Content-Type`.
- Чужой/несуществующий runId → 404, без утечки списка файлов.
- Path traversal отвергается (400/404), файл вне каталога не отдаётся.

## 9. EDGE CASES

Блок обязательных «плохих» сценариев: бюджет, падение Redis, невалидные ключи,
недоступная БД, нагрузка. Все кейсы — `P1`/`P2`, потому что именно здесь чаще
всего «зелёный» релиз ломается в проде.

#### EDGE-01 — Бюджет: жёсткий лимит (`hard`)
**Приоритет:** P1
**Предусловие:** `WORKFLOW_RUN_MAX_COST_USD=0.01`,
`WORKFLOW_RUN_BUDGET_MODE=hard`; сценарий с LLM.
**Шаги:**
1. Запустить.
2. Посмотреть узел, прогресс-бар и `GET /runs/:id/budget`.
3. Проверить `node_runs.cost_usd`.
**Ожидаемый результат:**
- Узел останавливается с ошибкой бюджета после первого дорогого вызова
  (лимит проверяется **до** вызова провайдера).
- `GET /runs/:id/budget` → `ok=false`, `mode=hard`, `accumulated` ≈ лимиту.
- В шапке прогресс-бар показывает превышение, тултип содержит суммы в USD и ₽.

#### EDGE-02 — Бюджет: мягкий режим (`soft`)
**Приоритет:** P2
**Предусловие:** `WORKFLOW_RUN_BUDGET_MODE=soft`, лимит минимальный.
**Шаги:**
1. Запустить тот же сценарий.
2. Посмотреть, завершился ли он.
**Ожидаемый результат:**
- Выполнение **продолжается** после превышения, в шапке — предупреждение
  («Бюджет запуска исчерпан (режим soft)»).
- `GET /runs/:id/budget` → `mode=soft`, `ok=false`.
- Узлы не помечаются failed из-за бюджета.

#### EDGE-03 — Бюджет: цифры UI = API
**Приоритет:** P2
**Предусловие:** активный запуск (или сразу после завершения).
**Шаги:**
1. Зафиксировать значения прогресс-бара (`[data-run-budget]`,
   `[data-run-budget-max]`).
2. Вызвать `GET /runs/:id/budget`.
3. Сравнить.
**Ожидаемый результат:**
- Значения совпадают с точностью до округления (4 знака после запятой).
- Поля `mode`, `ok`, `remaining`, `estimated` присутствуют.
- Отрицательного `remaining` в UI не показывается.

#### EDGE-04 — Redis недоступен перед запуском
**Приоритет:** P1
**Предусловие:** Redis остановлен (`docker compose stop redis`).
**Шаги:**
1. Нажать «Запустить».
2. Подождать 30 секунд.
3. Поднять Redis и повторить запуск.
**Ожидаемый результат:**
- Быстрый и понятный отказ (тост/ошибка), без «вечного» статуса «Создаётся…».
- `POST /runs` возвращает 5xx с сообщением; стектрейс не уходит в браузер.
- После поднятия Redis запуск работает.

#### EDGE-05 — Redis падает во время запуска
**Приоритет:** P1
**Предусловие:** запуск идёт (media/агент).
**Шаги:**
1. Остановить Redis.
2. Подождать 30–60 секунд (job может считаться stalled).
3. Поднять Redis, дождаться повтора/завершения.
**Ожидаемый результат:**
- Поток SSE переподключается; при исчерпании — тост «Поток запуска не
  отвечает».
- Job не теряется: после рестарта он либо повторяется (бейдж «попытка N/M»),
  либо завершается со статусом `failed`.
- UI не зависает навсегда; повторный запуск доступен.

#### EDGE-06 — Невалидный ключ LLM-провайдера
**Приоритет:** P1
**Предусловие:** ключ выбранного провайдера испорчен (в `.env`), backend
перезапущен; каталог моделей при этом доступен.
**Шаги:**
1. Запустить сценарий с LLM.
2. Открыть панель узла.
3. Проверить логи backend.
**Ожидаемый результат:**
- Узел `failed`, в панели — понятный текст (401/403/invalid key), без ключа и
  заголовков авторизации.
- Другие узлы (например, media) не затронуты.
- Запуск завершается статусом «Ошибка», повтор доступен.

## 12. Что НЕ тестируем в этой версии

Явные ограничения v0.10.0 (не заводить как баги, но фиксировать как «ожидаемо»):

1. **Маршрутизация веток условия** — выходы T/F не управляют потоком; обе
   ветки продолжают выполняться.
2. **Режим «LLM-судья» у сравнения** — не реализован, селект неактивен.
3. **Отмена запуска из UI** — кнопки нет; статус `cancelled` возможен только
   на стороне сервера.
4. **Приглашение по email** — только по UUID.
5. **«Скопировать к себе» по публичной ссылке** — кнопка неактивна.
6. **Флажок «Разрешить копирование»** — не влияет на доступ.
7. **Realtime-совместное редактирование** — не поддерживается.
8. **3D/motion-генерация, MCP-инструменты, отдельный vector service** — вне
   релиза (DESIGN § 6).
9. **PDF в `document_gen`** — не реализован, только DOCX (KI-463).
10. **Разбор JSON/CSV в `read_file`** — селект «Формат» не применяется:
    узел отдаёт сырой UTF-8; `json`/`rows` появятся в v0.11.
11. **`overwrite=false` и CSV-сериализация в `write_file`** — не применяются:
    файл всегда перезаписывается, кодировка UTF-8.
12. **`data.title` в Markdown-режиме** — игнорируется (KI-465); в JSON-режиме
    работает.
13. **500 блоков и cross-origin `download`** — лимит блоков не проверяется
    (KI-462), атрибут `download` для S3 игнорируется (KI-466).
14. **`searchDepth`/`topic`/`includeAnswer` у `web_search`** — отложены
    (KI-461); в v0.10 только `maxResults`.
15. **Переподпись S3 по `storage_key`** — ключ пишется, но переподпись пока
    идёт по URL (KI-464).

## 14. Шаблон баг-репорта

```
### BUG — <краткое название>
**Кейс:** <ID из этого гайда, например CANVAS-14>
**Приоритет:** P1 / P2 / P3
**Окружение:** браузер + версия, ОС, `NODE_ENV`, commit hash
**Предусловие:** <состояние системы/данных>
**Шаги воспроизведения:**
1. …
2. …
**Ожидаемый результат:** <что должно быть по этому гайду>
**Фактический результат:** <что реально; скриншоты, JSON, логи>
**Воспроизводимость:** всегда / 3 из 5 / один раз
**Связанные KI:** KI-XXX (если похожая проблема уже есть)
**Гипотеза:** <если есть>
```

Правила:

1. Один баг = один тикет. Не смешивать косметику и блокеры.
2. Для визуальных багов — **два** скриншота: «до» и «после» (RULES 4.33).
3. Для API/SSE — приложить сырой ответ/событие (без секретов и токенов).
4. Если баг не воспроизводится — завести KI с пометкой «не воспроизвелось» и
   описанием окружения.
