# ADR 0003: Аудит действий — глобальный интерсептор, роль owner и best-effort запись (v1.0.0 S3)

**Дата:** 2026-11-02
**Статус:** Accepted
**Связано:** DESIGN v1.0 § 2.2, § 3.2, § 5; RULES 4.18/4.22/5.9; KI-565..573

## Контекст

DESIGN v1.0 § 2.2 требует журнал действий пользователей (`Login`,
`CreateWorkflow`, `UpdateWorkflow`, `DeleteWorkflow`, `ShareAccess`,
`RunWorkflow`), § 3.2 — таблицу `audit_logs` и эндпоинт `GET /admin/audit`
(только Admin), перехват мутирующих запросов. S3 должен дать фундамент,
который не потребует правок каждого сервиса и переживёт появление новых ручек.

Одновременно нужно определить: где ставить перехват (глобально vs в каждом
сервисе), что считать «администратором» (в S3 роли ещё нет), как быть с
безопасностью metadata и с недоступностью журнала.

## Решение

1. **Глобальный `AuditInterceptor` (APP_INTERCEPTOR), а не вызовы в сервисах.**
   Перехватываются только `POST`/`PATCH`/`DELETE`; `GET`/`HEAD`/`OPTIONS` и
   `/auth/*` пропускаются. Автор и арендатор берутся из `request.user`
   (`JwtPayload` → `WorkflowAccess`); действие определяется по методу и
   фактическому пути (`resolveAuditAction`, таблица 13 маршрутов + fallback
   `http.<method>`); `resource_id` — из тела ответа (`.id`, uuid-валидация) либо
   `params.id`.
2. **Пишутся только успешные операции** — в `tap(next)`; упавшие запросы
   (валидация/права/ошибки) не журналируются (журнал фиксирует действия, а не
   попытки; аудит попыток — отдельная задача S5, KI-569).
3. **Запись best-effort (fire-and-forget).** Аудит — вспомогательная
   подсистема: INSERT не задерживает ответ, его ошибки только логируются
   (`RULES 4.18`). Цена — окно потери при падении процесса (KI-567);
   гарантированный аудит потребует transactional outbox и решается отдельно.
4. **Metadata санитизируется.** Удаляются ключи, похожие на
   password/token/secret/apiKey/authorization/cookie, на любой глубине; тело
   ограничено 16 KiB (`{truncated, bytes}`), исходный запрос не мутируется.
   Понимая, что тело workflow может содержать промпты (RULES 5.9), риск
   зафиксирован в KI-572 (в S5 — хэш/сводка вместо тела для крупных сущностей).
5. **Роль: `users.role` (`owner|admin|member|viewer`) + миграция.** Полноценных
   ролей организации в S3 нет; вводится одна роль пользователя с CHECK.
   Существующим 69 пользователям миграция 0015 проставляет `owner` (после S1
   каждый — единственный член своей личной организации), `registerAsync` сразу
   создаёт создателя `owner`, DEFAULT — `member` (для будущих участников S5).
6. **`GET /admin/audit` — `JwtAuthGuard` + `OrgOwnerGuard`.** Guard читает роль
   из БД по `user.sub` на каждый запрос (немедленный отзыв прав; один
   index-lookup по PK), допускает `owner`/`admin`, иначе 403. Чтение
   keyset-пагинацией (`created_at DESC, id DESC`, µs-курсор, `limit+1`,
   `nextCursor`, `total`) и только по своей организации (`organization_id`).
7. **Схема — append-only на уровне приложения.** `AuditService` не делает
   UPDATE/DELETE; retention/immutability на уровне БД не задаются (KI-565).
   Удаление пользователя/организации каскадно удаляет журнал арендатора —
   политика хранения открыта до S5.

## Последствия

**Лучше:**
- Аудит включается одним провайдером: новые мутирующие ручки покрываются без
  правок сервисов, код действий централизован.
- Секреты не попадают в журнал даже при ошибке валидации тела; metadata
  ограничен по размеру и глубине.
- Журнал изолирован по организации и доступен только owner/admin; типов
  ролей достаточно для S5 (участники/админы).
- Сбой аудита не ломает пользовательские операции; ответ не замедляется.

**Хуже / ограничения:**
- **Login/Register не аудируются** (нет автора в момент интерсептора, тело —
  секрет): DESIGN § 2.2 закрывается сервисным аудитом в S5 (KI-566).
- **Аудит best-effort**: возможна потеря записи при падении процесса; запись не
  входит в транзакцию бизнес-операции (KI-567).
- **Неудачные операции не журналируются** — нет аудита попыток/отказов прав
  (KI-569), что важно для безопасности.
- **Metadata может содержать пользовательские промпты** (тело workflow) —
  компромисс S3 по постановке; закрытие в S5 (KI-572).
- **Таблица маршрутов ручная**: переименование ручки деградирует код действия
  до `http.<method>` (KI-568).
- **Роль пользователя глобальна**, не привязана к членству в организации;
  при multi-org (S5) потребуется `organization_members` (KI-570).
- Retention/immutability и UI аудита — S5 (KI-565/KI-573).
