# ADR 0006: Письма-приглашения — опциональный SMTP и best-effort отправка (v1.1.0 S1)

**Дата:** 2026-11-03
**Статус:** Accepted
**Связано:** DESIGN v1.1 § 3.1, § 4, § 6; RULES 4.35, 5.3, 5.9; KI-584, KI-592..597

## Контекст

v1.0.0 S5 сделал командную работу возможной, но приглашение жило только в БД:
владелец должен был сам сообщить приглашённому адрес, а `POST
/admin/members/invite` отвечал «Приглашение отправлено» (KI-584). DESIGN v1.1
§ 3.1 требует интеграцию с `nodemailer`, письмо со ссылкой на регистрацию и
**обязательный fallback**: если SMTP не настроен, приглашение всё равно
создаётся, а сервис пишет WARN.

Ограничения, влияющие на решение:

1. SMTP — внешняя подсистема: недоступность провайдера/таймаут не должны ломать
   создание приглашения (приглашение — это строка БД, письмо — уведомление).
2. Backend не знает публичный домен: share-ссылки в проекте умышленно
   относительные (`ShareTokenDto.shareUrl`), абсолютный URL собирает клиент.
   Письму абсолютный URL **обязателен**.
3. Локализация шаблонов в v1.1.0 не входит (DESIGN § 6), профиля locale у
   пользователя нет.
4. `z.coerce.boolean()` в env запрещён (RULES 4.35): `'false'` превратился бы в
   `true`, и `SMTP_SECURE` включил бы implicit TLS на порту 587.

## Решение

1. **SMTP — опциональная подсистема с single-point конфигурацией.**
   `SmtpEnvSchema` (в `EnvSchema` через `.shape`): `SMTP_HOST`, `SMTP_PORT`
   (default 587), `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` (default
   `noreply@workflow-builder.local`), `SMTP_SECURE` (строгий boolean, default
   false), `APP_PUBLIC_URL` (default `http://localhost:3000`). Признак «почта
   настроена» — только `SMTP_HOST`; auth передаётся лишь когда заданы и user, и
   pass (локальный mock-SMTP не получает пустые креды).
2. **`EmailService` возвращает `boolean`, а не бросает.** `true` — SMTP принял
   письмо; `false` — не настроен (WARN) или отказ (ERROR). Вызывающий код
   (`OrgMembersService`) не оборачивает вызов в try/catch и не превращает
   успешное приглашение в 500. Таймауты транспорта — 10/10/20 с, чтобы зависший
   SMTP не держал HTTP-запрос минутами.
3. **Письмо не является частью транзакции приглашения.** Сначала INSERT
   приглашения (единственная точка правды для вступления по email), затем
   отправка. `POST /admin/members/invite` отвечает 201 и в любом случае, а
   результат отправки сообщает новым полем `emailSent` (отдельный DTO
   `InviteMemberResponse` — `OrganizationInvitationSummary` + флаг). UI разными
   сообщениями говорит «письмо отправлено» и «создано, но не отправлено».
4. **Ссылка — по идентификатору приглашения, а не по email.**
   `buildInvitationLink(invitationId)` → `${APP_PUBLIC_URL}/login?invite=<uuid>`:
   email (PII) в URL не попадает, id непрозрачен. `APP_PUBLIC_URL` — явная env,
   а не `Host` из запроса: host-header injection недопустим, а публичный домен
   приложения не выводится из внутреннего запроса.
5. **Шаблон — отдельный модуль чистых функций.** `email.templates.ts`:
   `sanitizeHeaderValue` (CR/LF и управляющие коды → пробел, защита от header
   injection), `escapeHtml` (имя организации задаёт пользователь), HTML+text
   части (антиспам-фильтры и клиенты без HTML). Тема — по постановке
   «Приглашение в организацию {orgName}».
6. **Логи без PII и секретов.** Email маскируется (`a***@example.com`), пароль
   SMTP не логируется даже в тексте ошибки (RULES 5.3, 5.9); в лог попадают
   только факт отправки/ошибки и причина отказа провайдера.
7. **Ошибка отправки не ретраится (v1.1.0 S1).** Очередь/BullMQ, колонки
   статуса и resend-ручка осознанно вынесены в KI-592/593/597: S1 — интеграция
   транспорта и шаблона, а не подсистема доставки.

## Последствия

**Лучше:**
- Приглашённый получает письмо со ссылкой; тема и текст содержат название
  организации; клик по кнопке открывает страницу входа/регистрации.
- Ненастроенный/упавший SMTP не ломает приглашение: 201, запись в БД, WARN или
  ERROR, `emailSent: false`; UI честно сообщает об этом.
- `SMTP_SECURE` не может «молча включиться» из строки `'false'` (RULES 4.35);
  пустая переменная — «не задана» (KI-084).
- Шаблоны тестируются без почтового сервера, а смоук проверяет реальный
  SMTP-диалог через mock-сервер.

**Хуже / ограничения:**
- Отправка синхронна: SMTP-задержка входит в latency `POST
  /admin/members/invite` (KI-592); ретраев и статуса доставки нет (KI-593).
- `?invite=<uuid>` UI не использует — регистрация по-прежнему «сжигает»
  приглашение по email (KI-594); письмо только на русском (KI-595).
- Нет отдельного rate limit на приглашения — возможен спам с домена продукта
  (KI-596); `emailSent` не сохраняется в БД, статус виден только в ответе на
  инвайт (KI-597).
