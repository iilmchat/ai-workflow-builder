# ADR 0001: Стратегия миграции данных при введении организаций (v1.0.0 S1)

**Дата:** 2026-11-02
**Статус:** Accepted
**Связано:** DESIGN v1.0 § 3.1, § 4; RULES 3.10, 4.22, 4.29, 4.30; KI-552, KI-553, KI-556

## Контекст

В v1.0.0 вводится мультитенантность (DESIGN_V100_ENTERPRISE § 3.1): таблица
`organizations`, обязательные (`NOT NULL`) колонки `organization_id` в `users` и
`workflows`, `orgId` в JWT. На момент релиза локальная БД содержит 69
пользователей и 160 workflow (в прод-подобных средах — аналогично), поэтому
вариант «`ALTER TABLE ... ADD COLUMN ... NOT NULL` в одной SQL-миграции» падает
без DEFAULT: PostgreSQL не знает, чем заполнить существующие строки.

Дополнительно DESIGN § 4 объявляет инвалидацию старых JWT: payload меняется,
и токены без `orgId` не должны приниматься guard'ом.

Нужно решить: (1) где выполняется backfill (в SQL-миграции или в скрипте
`migrate.ts`), (2) как обеспечить идемпотентность и безопасный порядок
«данные → ограничение», (3) как аутентификация переживает смену payload.

## Решение

1. **Миграция 0014 добавляет колонки nullable.** `drizzle-kit generate` создаёт
   SQL, `ADD COLUMN "organization_id" uuid` в нём вручную лишён `NOT NULL`
   (SQL-миграция — единственное место, где порядок «данные → ограничение»
   невозможно выразить одной DDL-инструкцией безопасно для непустой БД).
   Снимок Drizzle при этом соответствует `schema.ts` (`NOT NULL`): итоговое
   состояние БД после полного прогона `pnpm db:migrate` совпадает со схемой.
2. **Backfill — отдельный идемпотентный модуль
   `src/db/migrations/backfill-organizations.ts`**, вызываемый из `migrate.ts`
   сразу после `migrate()` в одной транзакции (`BEGIN`/`COMMIT`/`ROLLBACK`):
   - демо-организации детерминированный id
     (`00000000-0000-0000-0000-000000000002`);
   - каждому пользователю без организации — «Personal Workspace - {email}»
     (с `NOT EXISTS`-защитой от дублей при повторном прогоне);
   - пользователь привязывается к организации по имени;
   - workflow наследует организацию владельца (`workflow.user_id →
     users.organization_id`);
   - DO-блок падает понятной ошибкой, если остались строки без организации
     («осиротевшие» workflow не переприсваиваются молча);
   - только после проверки — `SET NOT NULL` для обеих колонок.
3. **Backfill — часть `migrate.ts` (а не SQL-миграции)**, потому что проект
   применяет миграции только через `pnpm db:migrate`/`node dist/migrate.js`
   (RULES 3.10, `docker-entrypoint.sh`, шаг CI `Apply migrations`), а
   идемпотентный TS-модуль можно покрыть интеграционным тестом на scratch-схеме
   без блокировки публичных таблиц.
4. **Старые JWT инвалидируются guard'ом.** `JwtPayload` получает обязательный
   `orgId`; `JwtAuthGuard` после проверки подписи отвергает токены без
   непустого `orgId` (401 «Токен устарел…»). Сессия восстанавливается
   `POST /auth/refresh` (refresh-cookie не менялась), иначе — повторный вход.
5. **Пометка в БД: проверка полноты и NOT NULL — в одной транзакции.** Если на
   проде найдётся workflow с `user_id`, которого нет в `users`, миграция
   прерывается с количеством строк (без PII), а не присваивает данные
   произвольной организации.

## Последствия

**Лучше:**
- Миграция безопасна для непустой БД и воспроизводима на чистой (проверено на
  scratch-БД: 15 миграций + backfill = 1 демо-организация, 0 NULL).
- Повторный запуск `pnpm db:migrate` идемпотентен (проверено: 69 организаций
  до и после, дублей имён 0).
- Backfill покрыт интеграционным тестом (создание, идемпотентность, пустые
  таблицы, NOT NULL) и не блокирует `public`.
- Старые токены не дают доступа с «пустым арендатором»; переход сессии
  бесшовный при живой refresh-cookie.

**Хуже / ограничения:**
- `SET NOT NULL` выполняется скриптом: прямой `drizzle-kit migrate`/`db:push` в
  обход `migrate.ts` оставит колонки nullable. Ловится parity-гейтом KI-298 в
  CI; эксплуатационное правило — только `pnpm db:migrate` (KI-556).
- `SET NOT NULL` берёт `ACCESS EXCLUSIVE` на `users`/`workflows`; в
  Docker/CI миграция идёт до старта приложения, но долгая транзакция во время
  миграции заблокирует DDL.
- Скрипт зависит от констант `src/auth/auth.constants.ts` (`DEMO_USER_ID`,
  `DEMO_ORG_ID`): переименование экспортов ломает `pnpm build:migrate`.
- DESIGN § 3.1 перечисляет ещё `document_templates` и `workflow_runs`; в S1 по
  постановке они не входят — вынесено в KI-552 (S2).
