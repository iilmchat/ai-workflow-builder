# ADR 0011: LLM Router — маршрутизация, таймаут и healthcheck в одном слое

**Дата:** 2026-11-06
**Статус:** Accepted
**Связано:** DESIGN v1.2 § 3.1–3.2; RULES 4.19, 4.35, 5.9; KI-617..621

## Контекст

1. До v1.2 LLM-вызов всегда уходил в облако: `LlmService` резолвил провайдера
   по id модели и вызывал его. Локальный LM Studio был доступен как обычный
   провайдер, но автоматического приоритета у него не было.
2. Требуется «умный роутер»: сначала локальный GPU-бэкенд, при ошибке —
   облачный fallback. У `LlmService` уже были свои обязанности: резолв
   провайдера, семафор на провайдера (KI-067), span `llm.call` (KI-365) и
   таймаут 60 с (RULES 4.19).
3. Прямолинейное решение «роутер только выбирает провайдера, а вызывает
   `LlmService`» ломается на fallback: провайдер становится известен только
   после ошибки, поэтому семафор и span нужно ставить на фактический вызов, а
   не на исходный.
4. Таймаут, созданный один раз на маршрут, делает fallback бессмысленным:
   после `AbortSignal.timeout` локальной попытки общий signal уже `aborted`, и
   облачный вызов падает мгновенно.
5. Для маршрутизации нужен признак доступности локального сервера. Пинг
   `GET /v1/models` на каждый LLM-вызов добавляет последовательный round-trip;
   пинговать нужно периодически и кэшировать статус.

## Решение

1. **Роутер владеет вызовом целиком.** `LlmRouterService.generateAsync`
   принимает `(prompt, options)` и сам:
   - выбирает локальный/облачный маршрут;
   - берёт слот `ProviderSemaphoreRegistry` по **фактическому** провайдеру;
   - создаёт span `llm.call` на весь маршрут (включая fallback) и проставляет
     `llm.provider`, `llm.local`, `llm.model_used`, `llm.wait_ms`, токены;
   - ставит таймаут 60 с **на каждую попытку** (`AbortSignal.timeout`), если
     вызывающий код не передал свой signal.
   `LlmService` остаётся тонкой обёрткой с прежним API.
2. **Отмена пользователя не запускает fallback.** Если `options.signal`
   `aborted`, роутер пробрасывает ошибку локальной попытки, а не повторяет
   вызов в облако: это отмена, а не сбой провайдера.
3. **Контракт доступности.** `ILlmProvider.isAvailableAsync()` — обязательный
   метод. Облачные провайдеры возвращают `true` без сети (ключ проверен
   `isConfigured`); `LmStudioProvider` пингует `GET {baseURL}/models` с
   таймаутом 3 с и трактует любую ошибку как `false`.
4. **Healthcheck кэширует статус.** `LlmHealthService` раз в 30 с пингует
   локального провайдера, после 3 неудач подряд ставит `unavailable` и
   исключает его из роутинга; успех возвращает `available`. Статус in-memory,
   таймер создаётся через `setInterval` + `unref()` и снимается в
   `onModuleDestroy`. `unknown` означает «проверить по факту»; параллельные
   проверки склеиваются одним `Promise`.
5. **Fallback-модель.** `LLM_ROUTER_FALLBACK_MODEL` (default `gpt-4o-mini`)
   резолвится в облачного провайдера; если модель не объявлена, берётся первая
   модель первого облачного провайдера с WARN. Локальный провайдер для
   fallback не используется.
6. **Выбор локальной модели.** Если выбранная модель объявлена LM Studio — она
   и уходит; иначе первая локальная модель (облачные id локально отсутствуют).
   Подмена — осознанный компромисс, ограничение зафиксировано в KI-617.
7. **Совместимость.** `LLM_ROUTER_ENABLED` по умолчанию `false`: без флага
   поведение прежнее (провайдер по модели). Строгий разбор boolean (RULES
   4.35), пустая строка — «не задано» (KI-084).

## Последствия

**Лучше:**
- Один слой отвечает за маршрут, таймауты, лимиты и tracing; `LlmService` и
  executor'ы не знают о fallback.
- Семафор применяется к тому провайдеру, который реально обслужил вызов, —
  лимит LM Studio не расходуется на облако и наоборот.
- Истёкший таймаут локальной попытки не отменяет облачный fallback.
- Healthcheck не пингует сервер на каждом вызове и не удерживает процесс
  живым (`unref`).
- Флаг по умолчанию выключен: релиз обратно совместим.

**Хуже / ограничения:**
- Модель и её возможности (vision/reasoning/tools) не сверяются при
  маршрутизации — KI-617.
- Fallback-модель из env может подмениться первой моделью облака — KI-619.
- Статус healthcheck локальный для процесса: при нескольких инстансах N
  пингов и возможное расхождение — KI-620; восстановление замечается с
  задержкой до 30 с — KI-621.
- Один LLM-вызов может занять до 120 с при двух таймаутах (локальный +
  облачный); это меньше lock'а BullMQ (5 мин), но больше прежних 60 с.
- Healthcheck работает и при `LLM_ROUTER_ENABLED=false` (нужен будущему
  UI-индикатору), то есть при настроенном LM Studio даёт один `GET /models`
  в 30 с.
