# ADR 0005: Команда организации — приглашения по email и потребление при регистрации (v1.0.0 S5)

**Дата:** 2026-11-03
**Статус:** Accepted
**Связано:** DESIGN v1.0 § 2.1, § 3.2, § 5; RULES 1.17/4.22; KI-554/555/563/570/583/584/586/588

## Контекст

DESIGN v1.0 § 2.1 вводит организацию как арендатора и роли
`owner`/`admin`/`member`/`viewer`. К S4 в продукте есть: `organizations`
(S1), `users.organization_id` + `users.role` (S1/S3), org-изоляция workflow
(S2), журнал `audit_logs` и `GET /admin/audit` (S3). Командной работы при этом
нет: каждый пользователь — единственный член своей личной организации, а
`GET /auth/me` не отдаёт ни организации, ни роли (KI-555), пригласить в
организацию некого (KI-563).

Ограничения модели, которые нельзя обойти в S5:

1. **Отдельной таблицы членства нет.** Организация пользователя — это
   `users.organization_id`, роль — `users.role` (одна на пользователя, KI-570).
2. **Workflow привязаны к `organization_id`** (S2). Переписать
   `users.organization_id` зарегистрированному пользователю нельзя: его графы
   останутся в прежней организации, и он потеряет к ним доступ.
3. **Транспорта почты в проекте нет** (ни SMTP, ни transactional-провайдера).

## Решение

1. **Приглашение — отдельная сущность, а не пользователь.** Новая таблица
   `organization_invitations(id, organization_id, email, role, invited_by,
   created_at)` с `UNIQUE (organization_id, email)`, индексом по `email` и CHECK
   роли (`admin|member|viewer`). Приглашённый ещё не зарегистрирован, поэтому
   `users`-строка заранее не создаётся (нет `password_hash`), а
   `organization_invitations` фиксирует намерение владельца.
2. **Инвайт по email, а не по uuid.** `POST /admin/members/invite`
   (`owner`/`admin`) принимает `{ email, role }`; email нормализуется
   (trim + lower case), как в `AuthService.registerAsync`. Владелец не
   назначается инвайтом (`owner` — создатель организации), поэтому домен роли
   приглашения — `INVITABLE_USER_ROLES` из `src/db/schema.ts` (единый источник
   для CHECK, Zod и типа).
3. **Приглашение «созревает» при регистрации.** `AuthService.registerAsync`
   перед созданием личной организации ищет **самое старое** приглашение по
   email (порядок `created_at ASC, id ASC`); если оно есть — создаёт
   пользователя в организации пригласившего с указанной ролью и удаляет строку
   приглашения **в той же транзакции** (RULES 4.22). Нет приглашения — прежнее
   поведение: личная организация + `owner`.
4. **Организация и роль — из БД, а не из токена.** `/admin/members*` получают
   только `user.sub`; `OrgMembersService` резолвит `organization_id` по строке
   `users`, `OrgOwnerGuard` читает там же роль. Устаревший `orgId` в access-токене
   (24 ч) не уводит операцию в чужой арендатор (KI-554 для этих ручек закрыт;
   `GET /admin/audit` остался на токене — KI-587).
5. **Две политики доступа на одном контроллере.** `GET /admin/members` —
   `JwtAuthGuard` (состав команды нужен любому участнику), `POST
   /admin/members/invite` — плюс `OrgOwnerGuard` (`owner`/`admin`, 403
   остальным). `OrgOwnerGuard` экспортируется из `AuditModule`, чтобы политика
   административных ручек оставалась в одном месте.
6. **Публичный профиль.** `UserPublic` дополняется `organizationId` и `role`
   (из строки `users`); поля приходят во всех ответах с пользователем
   (`/auth/me`, login, register, refresh). Имя организации не добавляли — UI его
   не показывает, лишний join не нужен.
7. **Контракт — гейт.** Новые REST-ответы (`UserPublic`,
   `OrganizationMemberSummary`, `OrganizationInvitationSummary`,
   `OrganizationMembersResponse`, `AuditLogSummary`, `AuditLogsResponse`) и
   домены ролей добавлены в `docs/development/api-contract.json`, backend-spec и
   web-зеркала — расхождение сторон падает в CI (KI-352).
8. **Аудит приглашения.** Код `member.invite` добавлен в `AUDIT_ACTIONS` и
   таблицу маршрутов: приглашение в организацию — действие команды, журнал
   должен его видеть. Email в metadata остаётся (это смысл записи), пароли и
   токены интерсептор вырезает.
9. **UI — модалка, а не страница.** `TeamPage` открывается из `TopBar`
   (👥 «Команда») и повторяет `RunHistoryModal`: оверлей `z-40`, Escape/фон/✕.
   Вкладка «Аудит» грузится лениво и только для `owner`/`admin` (backend отвечает
   403 остальным); пагинация — keyset по `nextCursor`, как у истории запусков.

## Последствия

**Лучше:**
- Командная работа стала возможной: владелец приглашает email, приглашённый
  регистрируется и сразу оказывается в нужной организации с нужной ролью;
  `GET /admin/members` показывает состав и ожидающие приглашения.
- `GET /auth/me` отдаёт tenant и роль — UI больше не декодирует JWT вручную
  (KI-555 закрыт).
- Журнал аудита доступен из UI с keyset-пагинацией (KI-573 закрыт); действие
  приглашения видно в журнале.
- Ручки команды не доверяют токену в части организации — KI-554 закрыт для них.

**Хуже / ограничения:**
- Пригласить можно только ещё не зарегистрированный email; перенос
  существующего пользователя (и его workflow) между организациями — не решён
  (KI-583).
- Письма не отправляются, транспорт почты вне S5 (KI-584).
- Нет смены роли и удаления участника (KI-586); журнал без фильтров (KI-585);
  несколько организаций могут пригласить один email, «сжигается» только самое
  старое приглашение (KI-588).
- `users.role` остаётся глобальной (KI-570), список команды без пагинации
  (KI-590), модалка без deep-link (KI-591), `GET /admin/audit` по-прежнему
  доверяет `orgId` из токена (KI-587).
