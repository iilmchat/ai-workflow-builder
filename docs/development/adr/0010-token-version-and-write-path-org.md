# ADR 0010: Отзыв access-токена через `token_version` и организация из БД в write-путях

**Дата:** 2026-11-05
**Статус:** Accepted
**Связано:** DESIGN v1.1 § 3.5; RULES 1.17, 5.9; KI-589, KI-601, KI-605, KI-614..616

## Контекст

1. v1.1.0 S2 отзывает refresh-токены удалённого участника, но выданный
   access-JWT (24 ч) остаётся валидным. После переезда в личную организацию
   удалённый становится `owner` своей организации, а `orgId` в его старом
   токене указывает на прежнюю — это давало доступ к её данным (KI-601).
2. S3 закрыл **чтение** журнала (организация резолвится из `users`), но
   write-пути (`AuditInterceptor`, `WorkflowService.createAsync`) продолжали
   брать `orgId` из токена. Удалённый со старым токеном мог создать workflow в
   старой организации и записать строку в её аудит (KI-605, подтверждено
   смоуком S3).
3. В аудите `member.invite` metadata хранила email приглашённого в открытом
   виде (KI-589, RULES 5.9).
4. Нужен механизм немедленного отзыва access-токена: TTL 24 ч — слишком
   большое окно, blacklist по `jti` в Redis требует новой инфраструктуры.

## Решение

1. **`users.token_version` + `JwtPayload.ver`.** Добавлена колонка
   `token_version integer NOT NULL DEFAULT 0` (миграция
   `0018_daffy_triathlon.sql`). `AuthService.generateAccessTokenAsync` кладёт
   `ver: user.tokenVersion`. Токены, выпущенные до S5, не содержат `ver` и
   трактуются как версия 0 (DEFAULT колонки) — массового разлогина нет; после
   первого инкремента они перестают проходить.
2. **Guard сверяет токен с БД.** `JwtAuthGuard` после проверки подписи делает
   один SELECT `organization_id, token_version` по `sub`:
   - нет строки `users` → 401;
   - `organization_id !== payload.orgId` → 401;
   - `token_version !== payload.ver` → 401.
   При успехе в `request.user` кладётся payload с **актуальными** значениями
   из БД. Это закрывает и устаревшую организацию, и принудительный отзыв.
3. **Инкремент версии при удалении участника.** `OrgMembersService` в той же
   транзакции, что переезд и отзыв refresh-токенов, делает
   `token_version = token_version + 1`. После коммита старый access-токен
   удалённого получает 401 на любом маршруте.
4. **Организация в write-путях — из БД.** `WorkflowService.createAsync`/
   `importAsync` принимают только `userId` (sub) и резолвят
   `users.organization_id` (401, если строки нет); контроллеры
   `workflow`/`templates` передают `user.sub`. `AuditInterceptor` использует
   `request.user.orgId`, уже сверенный guard'ом с БД, поэтому отдельный SELECT
   в интерсепторе не нужен. Это defense in depth: guard защищает HTTP-путь,
   сервис — прямой вызов.
5. **Маскировка email.** Для действий `member.invite`/`member.remove`
   `AuditInterceptor` рекурсивно заменяет email-подобные подстроки на
   `a***@example.com` (домен сохраняется, локальная часть скрыта). Остальные
   действия не меняются: их metadata может быть нужна для расследований.
6. **Совместимость.** Формат токена расширен аддитивно (`ver`), старые токены
   без `ver` работают как версия 0. `orgId` остаётся в payload (его проверяет
   guard), но write-пути его больше не используют как источник истины.

## Последствия

**Лучше:**
- Удаление участника немедленно отзывает access-токен: 401 на `/auth/me`,
  `/workflow`, `/admin/audit`, `POST /workflow` (смоук 16/16).
- Устаревшая организация не проходит ни в чтение, ни в запись; guard —
  единая точка сверки.
- `WorkflowService` не может быть вызван с подложенной организацией даже в
  обход HTTP-guard'а.
- Email приглашённых/удалённых не хранится в журнале в открытом виде.

**Хуже / ограничения:**
- Каждый аутентифицированный запрос делает дополнительный SELECT в БД
  (KI-615); кэш не вводился, чтобы не создавать окно устаревания.
- Logout по-прежнему не отзывает access-токен: инкремент версии на logout
  отозвал бы все сессии пользователя, а не текущую (KI-614).
- Старые токены без `ver` считаются версией 0 — до первого инкремента они
  валидны; устаревший `orgId` при этом всё равно отклоняется.
- Маскировка включена только для `member.invite`/`member.remove`;
  `collaborator.invite` всё ещё пишет email (KI-616).
- Полный отзыв по `jti` (individual sessions) не реализован; `token_version`
  отзывает все access-токены пользователя.
