# ADR 0008: Организация аудита — из БД, фильтры журнала (v1.1.0 S3)

**Дата:** 2026-11-04
**Статус:** Accepted
**Связано:** DESIGN v1.1 § 3.3/§ 3.5; RULES 1.17, 3.10, 4.28; KI-585, KI-587, KI-601, KI-605

## Контекст

1. v1.0.0 S3 добавил журнал аудита и `GET /admin/audit`. Контроллер передавал
   в `AuditService.listAsync` контекст `toWorkflowAccess(user)`, то есть
   `organization_id` брался из access-токена (`JwtPayload.orgId`).
2. v1.0.0 S5 и v1.1.0 S2 уже резолвят организацию из `users` для
   `/admin/members*` (KI-554): access-JWT живёт 24 часа, и после переезда
   пользователя в другую организацию `orgId` в нём устаревает.
3. v1.1.0 S2 отзывает refresh-токены удалённого участника, но старый access-токен
   остаётся валидным. Удалённый становится `owner` своей личной организации,
   поэтому `OrgOwnerGuard` пропускает его к аудиту, а org-фильтр по устаревшему
   `orgId` отдаёт журнал организации, из которой его исключили (KI-587, KI-601).
4. KI-585 требует фильтры по действию, автору и датам; на большом журнале
   фильтрация без индексов деградирует.

## Решение

1. **Организация журнала — из БД.** `AdminAuditController.list` передаёт в
   `AuditService.listAsync` только `user.sub`. Сервис первым запросом читает
   `users.organization_id` по `users.id`; нет строки — 401. `JwtPayload.orgId`
   в коде чтения аудита не используется вообще (структурно: он не передаётся в
   сервис). Это закрывает вектор чтения KI-601; сам токен не отзывается —
   полный отзыв (token_version/blacklist) остаётся отдельной задачей.
2. **Фильтры — часть одного предиката.** `AuditQuerySchema` принимает
   `action` (точный код, формат `<сущность>.<глагол>`; домен не ограничен
   списком, чтобы fallback `http.<метод>` и новые действия работали без правки
   валидатора), `userId` (uuid автора), `from`/`to` (включительно).
   `from`/`to` принимают `YYYY-MM-DD` (UTC-сутки: начало/конец дня) и полный
   ISO-8601 с зоной. `from > to` — 400, а не пустая страница «молча».
3. **`total` считается по тому же предикату, что страница.** Org-условие и
   фильтры собираются один раз (`listFilter`) и используются в `count(*)` и в
   `SELECT`; курсор добавляется только к странице. Иначе счётчик «Показано N из
   M» показывал бы записи вне фильтра (KI-571).
4. **Индексы под фильтры.** Миграция `0017_kind_gorilla_man.sql`:
   `(organization_id, action, created_at, id)` и
   `(organization_id, user_id, created_at, id)`. Порядок колонок повторяет
   `WHERE` + `ORDER BY created_at DESC, id DESC`, поэтому фильтрованная
   страница не сортирует весь журнал в памяти. Существующий
   `(organization_id, created_at, id)` остаётся для диапазонов дат без
   action/user.
5. **UI — контролы, а не отдельный API действий.** В `TeamPage` селекты
   действия (захардкоженный список известных кодов) и автора (участники
   организации), два `<input type="date">` и «Сбросить». Изменение фильтра
   перезапрашивает первую страницу (курсор старого набора строк неприменим),
   «Загрузить ещё» передаёт те же фильтры. Даты локальных суток превращаются в
   ISO-моменты на клиенте, поэтому «с 1 ноября» — это 1 ноября по поясу
   пользователя, а не UTC.
6. **Контракт.** Состав REST-ответов не менялся. В
   `docs/development/api-contract.json` добавлена секция `queryParams` для
   `GET /admin/audit` — query-параметры не входят в field-level гейт ответов,
   но фиксируются рядом с ними.

## Последствия

**Лучше:**
- Устаревший `orgId` в access-токене не открывает журнал другой организации;
  удалённый участник видит только аудит своей новой организации (смоук 31/31).
- Фильтры работают вместе с keyset-пагинацией; `total` честно описывает
  отфильтрованный набор.
- Мусорные значения отклоняются на границе (400) — сервис не строит заведомо
  пустые запросы.
- Индексы под action/user добавляют стоимость только на запись аудита, а
  чтение с фильтрами перестаёт зависеть от размера журнала.

**Хуже / ограничения:**
- На страницу журнала теперь четыре запроса к БД: роль guard'а, резолв
  организации, `count(*)`, страница (KI-607).
- Список действий в UI захардкожен и требует правки при добавлении действия
  (KI-606).
- UI не предотвращает `from > to`: 400 показывается как общая ошибка загрузки
  (KI-608).
- Write-пути (`AuditInterceptor`, `POST /workflow`) по-прежнему берут
  `organization_id` из токена: удалённый участник может писать в старую
  организацию (KI-605). Это следующий шаг вместе с полным отзывом access-токена
  (KI-601).
