# ADR 0002: Изоляция организаций и семантика доступа к workflow (v1.0.0 S2)

**Дата:** 2026-11-02
**Статус:** Accepted
**Связано:** DESIGN v1.0 § 2.1, § 3.1, § 5; RULES 4.26; KI-559..564

## Контекст

S1 ввёл `organizations` и `organization_id` в `users`/`workflows`, но выборки
остались прежними: доступ определялся владельцем (`workflows.user_id`) или
строкой `workflow_collaborators`. Пользователь одной организации мог по uuid
открыть workflow другой (если он владелец/участник), а `sub_workflow`-ссылка
загружала подграф без проверки организации. Нужен единый предикат изоляции на
всех маршрутах: workflow, запуски, история, шаблоны документов, подграфы.

Одновременно нужно решить, **как сочетать** изоляцию арендатора с существующей
моделью доступа: роли организации (owner/admin/member/viewer) из DESIGN § 2.1
ещё не реализованы, а `workflow_collaborators` даёт точечный доступ конкретным
пользователям.

## Решение

1. **Доступ = совпадение организации И (владелец ИЛИ участник).** Предикаты
   `workflowAccessFilter`, `workflowAccessListFilter`, `workflowOwnerFilter`,
   `accessibleWorkflowIdsSubquery` получили условие
   `workflows.organization_id = access.orgId`; фильтр владельца/участника
   сохранён. `GET /workflow` возвращает только графы своей организации, к
   которым у пользователя есть доступ.
2. **Единый контекст `WorkflowAccess { userId, orgId }`** вместо пары строк в
   сигнатурах сервисов. Контроллеры собирают его только из подписанного
   access-токена через `toWorkflowAccess(user)` — подменить организацию через
   body/query нельзя.
3. **Чужой арендатор неотличим от несуществующего.** Все отказы — 404
   (сохраняет политику KI-202: факт существования не раскрывается), а не 403.
4. **Кросс-организационный инвайт запрещён**: `inviteCollaboratorAsync` ищет
   целевого пользователя с `users.organization_id = access.orgId`; и «нет
   такого», и «он в другой организации» дают один 404. Список участников
   фильтруется по организации арендатора — email чужой организации не
   отдаётся.
5. **Публичная share-ссылка — исключение**: `GET /workflow/share/:token`
   работает по capability-токену без org-фильтра (явное требование S2; R6.2.1).
6. **`sub_workflow` — org-scoped**: контекст движка получает `rootUserId` и
   `rootOrgId` (один join `workflow_runs → workflows`); если любой из них не
   определён — 404, подграф не загружается. Непроверенного lookup'а не осталось.
7. **Без изменений схемы БД и API-контракта**: колонки добавлены в S1, форма
   ответов не менялась, поэтому новых миграций и правок
   `docs/development/api-contract.json` нет.

## Последствия

**Лучше:**
- Изоляция арендаторов enforced на уровне SQL на всех чтениях/записях
  workflow, запусков, истории, шаблонов и подграфов; подделать `orgId` нельзя.
- Кросс-организационные участники не создаются и не дают доступа; чужой PII не
  показывается.
- Публичные share-ссылки сохраняют прежнюю capability-семантику.
- `WorkflowAccess` делает забытый `orgId` ошибкой компиляции, а не дырой.

**Хуже / ограничения:**
- **Совместная работа между организациями недоступна до S5** (KI-563): после
  бэкфилла S1 у каждого пользователя личная организация, а API создания
  организации/приглашения в неё появится только в S5. Легаси-строки
  `workflow_collaborators` (все кросс-организационные) де-факто заморожены:
  доступа не дают и скрыты из списка, но остаются в БД (KI-560).
- Семантика «org + user-level access» консервативнее, чем «все члены
  организации видят графы организации»; при появлении ролей в S5 её, возможно,
  придётся ослабить (DESIGN § 2.1 говорит о командах).
- Необязательный `access` во внутренних методах сохраняет пути без фильтра
  (KI-561); отсутствует DB-инвариант «организация workflow = организация
  владельца» (KI-564).
- Удаление организации может упасть на FK `invited_by` (KI-559) — вопрос
  политики удаления арендатора (S5, KI-558).
- SQL-shape тесты опираются на приватные структуры Drizzle (KI-562).
