# Синхронизация GitHub Issues — отчёт

## 1. Файлы

| Файл | Изменение |
|------|-----------|
| `scripts/reconcile-github-issues.mjs` | +140 (новый) — одноразовая сверка состояния Issues |
| `scripts/sync-known-issues.ps1` | +20 / −6 — REST-пагинация всех страниц и закрытие дубликатов |
| `docs/KNOWN_ISSUES.md` | уточнение KI-671 |

## 2. Причина

GitHub Issues — витрина реестра (RULES 2.4), но её состояние расходилось:
- `sync-known-issues.ps1` читал только последние **500** Issues, поэтому
  старые дубликаты (до 16 копий одного KI) никогда не закрывались;
- CI-задача синхронизации падала из-за GitHub API rate limit.

В реестре на момент сверки: 658 KI, **Open = 0**, Planned 3.

## 3. Что сделано

1. `scripts/reconcile-github-issues.mjs` — dry-run показал 3390 открытых
   KI-Issues: 3387 к закрытию, 3 канонические Planned-копии оставить открытыми.
2. Пилот на 3 Issue подтвердил: `state=closed`, `state_reason=completed /
   not_planned`, комментарий с итоговым статусом и ссылкой на реестр.
3. Полный прогон закрыл 3387 устаревших Issues (3381 за проход + 2 после
   TLS-timeout + 4 догнанных); история не удалялась — Issues остались в
   closed-состоянии с комментариями. Два PATCH с TLS-timeout (`#484`, `#483`)
   повторены вручную.
4. `sync-known-issues.ps1` исправлен: читает все страницы REST API и закрывает
   дубликаты, оставляя одну каноническую копию на KI.

## 4. Результат

- Открытых KI-Issues: **3** (канонические копии KI-006, KI-566, KI-572 —
  статус `Planned` в реестре).
- Все остальные mirror-issues закрыты с причиной `completed` (Fixed-подобные)
  или `not_planned` (Deferred/Won't Fix/Documented/Planned-дубли).
- Актуальная история сохраняется в реестре и в закрытых Issues с комментариями.

## 5. Что не так

- CI job «Sync KNOWN_ISSUES.md with GitHub Issues» может падать по rate limit
  после массовой сверки; это инфраструктурное ограничение, не расхождение данных.
- Комментарии добавлены только к каноническим копиям (290), чтобы не тратить
  лишние API-вызовы на дубликаты.
