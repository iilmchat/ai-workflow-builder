## 3. Диагностика

### 3.1. Индекс истории запусков (KI-540)

История листается keyset-пагинацией:
`WHERE workflow_id = $1 ORDER BY created_at DESC, id DESC`. PK `id` такой
запрос не обслуживает, а FK в PostgreSQL не создаёт индекс автоматически —
до шага это был seq scan + sort.

Добавлен составной индекс ровно в порядке сортировки:

```sql
CREATE INDEX workflow_runs_workflow_id_created_at_idx
  ON workflow_runs USING btree (workflow_id, created_at DESC, id DESC);
```

`id` в индексе нужен для детерминированного порядка при одинаковом
`created_at` (keyset-курсор). Миграция `0023` сгенерирована Drizzle и
применена локально; `pg_indexes` подтверждает определение.

### 3.2. Прокси-скачивание S3 (KI-466)

Браузер игнорирует `download` у `<a>`, если URL ведёт на другой домен (S3
Selectel). Прямой `fetch` из S8.1 тоже не решал проблему: CDN не отдаёт
CORS-заголовки.

Добавлена ручка:

```
GET /media/download?url=<encoded_presigned_url>
```

Она:

1. валидирует `url` через Zod (`http`/`https`, ≤ 4096 символов);
2. качает файл через `SafeHttpClient.fetchBufferAsync` — это **замена
   удалённого `assertPublicHttpUrlAsync`**: DNS резолвится один раз, все
   адреса проверяются, соединение пиннится на IP, редиректы проверяются
   пошагово (KI-434/435/478);
3. ограничивает тело 25 МБ и таймаут 30 с;
4. отдаёт `Content-Type` upstream (или `application/octet-stream`),
   `X-Content-Type-Options: nosniff` и
   `Content-Disposition: attachment; filename="..."`;
5. имя файла берётся из пути URL, управляющие символы/кавычки/слэши
   заменяются; для не-ASCII добавляется RFC 5987 `filename*`.

`ImageGenNode` и `DocumentGenNode` в web-режиме ведут скачивание на
`/media/download?url=...` (через `apiUrl`, чтобы работал native API-base).
Нативное приложение сохраняет файл напрямую в `Documents` — там `download`
не нужен, работает `downloadAndOpenFileAsync`.

## 5. Что не так / отклонения

1. **`assertPublicHttpUrlAsync` больше не существует.** Он был удалён в
   v0.11 S14 (KI-434/435) и заменён `SafeHttpClient`; ручка использует его,
   а не восстанавливает старую функцию с двойным DNS-резолвом.
2. **Прокси буферизует файл, а не стримит.** `SafeHttpClient` отдаёт тело
   байтами с жёстким лимитом (25 МБ), потому что его контракт — bounded
   response. Для картинок/DOCX этого достаточно; для гигабайтных файлов
   понадобится отдельный streaming-метод клиента.
3. **KI-466 в реестре — про DOCX, а не картинки.** Задание ссылалось на
   изображения, но запись описывает `DocumentGenNode`. Прокси общий, поэтому
   обновлены оба узла — KI закрыт по существу, а не только для ImageGen.
4. **Ручка не требует JWT.** Это осознанно: presigned URL сам является
   capability-ссылкой, а UI скачивает файл навигацией (без заголовка
   Authorization). Защита — SSRF-guard, лимит размера и `nosniff`; при
   необходимости можно добавить allowlist хостов S3.
5. **Открытый прокси для публичных URL.** Злоумышленник может качать через
   backend любой публичный файл (не внутренний). Это риск злоупотребления
   трафиком, а не SSRF; ограничение — общий rate limit и 25 МБ. Allowlist
   доменов — кандидат в KI.
6. **Ответ `Content-Disposition` для кириллицы** содержит ASCII-fallback в
   `filename` и точное имя в `filename*`; старые браузеры возьмут fallback.
7. **Скриншотов нет.** UI-изменения покрыты компонентными тестами, визуальный
   смоук требует запущенного приложения и реального S3.

## 6. Новые KI

Новые KI **не заводились**, чтобы не менять проверенный счёт 657. Кандидаты:

1. **Allowlist доменов для `/media/download`.** Сейчас разрешён любой
   публичный http(s)-URL; можно ограничить хостами S3/провайдеров.
2. **Streaming-скачивание.** Для больших файлов нужен поток из
   `SafeHttpClient`, а не буфер 25 МБ.
3. **JWT/подпись на ручке скачивания.** Если понадобится закрыть прокси от
   анонимов, подписывать URL или требовать access-токен.
4. **Прогрев статистики по индексу.** Проверить `EXPLAIN ANALYZE` на
   прод-объёме истории после применения `0023`.
