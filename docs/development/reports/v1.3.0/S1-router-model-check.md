## 3. Диагностика

### 3.1 Что именно было не так до S1

Роутер подменял модель в двух местах **вслепую**:
1. `pickLocalModel` брал выбранную локальную модель или, если её нет в
   каталоге LM Studio, **первую** локальную — без проверки модальностей;
2. `resolveCloudRoute` брал `LLM_ROUTER_FALLBACK_MODEL` (или первую модель
   облака), не сверяя её с исходной.

Практический сценарий отказа: пользователь выбрал `gpt-4o` (vision) в
vision-узле; в LM Studio только текстовая модель → вызов уходил в неё и падал
на 400 от upstream; ошибка выглядела как «провайдер отказал», а не «роутер
выбрал неподходящую модель».

### 3.2 Почему требования строятся из паспорта, а не из узла

В `LlmGenerateOptions` нет признака «в запросе есть изображения»: исполнитель
узла передаёт только `prompt` и `system`. Поэтому единственный доступный
роутеру источник требований — паспорт **исходной модели** (если она vision,
значит подменять её текстовой нельзя). Это осознанно консервативно и
зафиксировано как KI-630: для чисто текстовой задачи с vision-моделью роутер
всё равно требует vision и потому не идёт на текстовый GPU. В смоуке это
видно в фазе 1 (LM Studio не вызывался).

### 3.3 Контекст: `maxTokens` vs `defaultMaxTokens`

`ModelInfo` уже содержал `defaultMaxTokens` — это лимит **ответа** (KI-183),
а не размер контекста. Для сверки нужен контекст (вход + выход), поэтому
добавлено отдельное поле `maxTokens`. Значения проставлены для встроенных
каталогов; для моделей из env (`LMSTUDIO_MODELS`, `GPTUNNEL_MODELS`,
`YANDEX_MODELS`) оно неизвестно (`0`), и проверка пропускается — «неизвестно»
не является доказательством несовместимости (KI-629).

### 3.4 `supportsTools` по умолчанию = `true` для текстовых моделей

Инструменты агента в текущей реализации передаются **промптом** (в
`ILlmProvider.generateAsync` нет нативных `tools`), поэтому любая текстовая
модель технически способна вести tool-цикл. Явный `false` стоит только у
`deepseek-reasoner` (у R1 tool-calling не поддержан). Эвристика зафиксирована
в KI-631 — она не доказывает, что модель корректно следует протоколу.

### 3.5 Ключевая ловушка смоука: `.env` подмешивал чужие ключи

Первый прогон фазы 3 дал `completed` вместо ожидаемого `failed`: backend
получал `.env` с реальными ключами, и после отказа локальной модели fallback
находил **Yandex**-модель с vision (`qwen3.6-35b-a3b`), совместимую с
требованием. Сообщение в логе было корректным
(«Модель fallback "deepseek-chat" несовместима … использую gpt://… (yandex)»),
но смоук проверял не то окружение. Исправление: фаза явно зануляет
`ANTHROPIC_API_KEY`, `ROUTERAI_API_KEY`, `GPTUNNEL_API_KEY`, `YANDEX_*`
(включая `YANDEX_API_KEY`/`YANDEX_IAM_TOKEN`, которых не было в первой
версии), оставляя только свой mock-провайдер. После этого фаза 3 даёт
`failed` ровно с ожидаемым текстом.

### 3.6 Смоук-процесс не завершался: mock-серверы не закрывались

Первая версия скрипта держала `http.Server` открытыми, из-за чего Node не
выходил из процесса после `mainAsync` (job пришлось прервать). Добавлены
`localServer`/`cloudServer` и `stopMocksAsync()` в `finally`-уборке; повторные
прогоны завершаются сами, порты свободны.

### 3.7 Почему реестр в тестах роутера стал настоящим

Фейковый реестр в `llm-router.service.spec.ts` (простой объект с четырьмя
методами) после S1 пришлось бы синхронизировать с `getCapabilities` и
`findCompatibleRoute` вручную — и тест мог бы «зеленеть» при рассинхроне
реализации. Теперь `createRouter` собирает `new LlmRegistryService(providers)`
из провайдеров-заглушек: проверяется реальная логика сверки, а заглушки
задают только паспорта моделей. Это же убрало из теста дублирование
`resolveByModel`.

### 3.8 Изменения поведения, которые видно снаружи

1. **vision-модель + текстовый локальный GPU → облако** (раньше — локальный
   вызов с падением). Медленнее по стоимости, но корректнее.
2. **fallback теперь предпочитает исходную модель пользователя**, а не модель
   из `LLM_ROUTER_FALLBACK_MODEL`: при `gpt-4o` + упавший локальный вызов
   уходит `gpt-4o`, а не `gpt-4o-mini`. Модель из env используется, только
   если исходная недоступна как облачная или несовместима.
3. **Нет совместимой модели → `failed`** с текстом «нет облачной модели,
   совместимой…», а не тихий вызов неподходящей.
4. При `LLM_ROUTER_ENABLED=false` ничего не меняется: сверка не выполняется
   (пользователь выбрал модель явно, подмены нет).

## 5. Что не так

1. **Vision требуется всегда, если исходная модель vision-ная (KI-630, 🟢 Low).**
   Для текстовой задачи на `gpt-4o` с текстовым GPU локальный вызов теперь не
   делается (смоук, фаза 1): платим за облако там, где раньше работал GPU.
   Лечение — передавать фактические модальности запроса из исполнителя узла,
   а не выводить их из паспорта модели.
2. **Контекст не сверяется для env-каталогов (KI-629, 🟢 Low).**
   `LMSTUDIO_MODELS`/`GPTUNNEL_MODELS`/`YANDEX_MODELS` не задают `maxTokens`,
   поэтому для них проверка контекста выключена (`0` = неизвестно). Длинный
   промпт в маленькую локальную модель по-прежнему даст отказ провайдера.
3. **Паспорта — статический снимок (KI-631, 🟢 Low).** `supportsTools` и
   `maxTokens` для встроенных каталогов выписаны константами по состоянию на
   2026-11-06; при смене моделей у провайдера они разойдутся с реальностью.
   `supportsTools` для текстовых моделей — эвристика (`true`), потому что
   инструменты агента передаются промптом.
4. **Явного маппинга «облачная → локальная» нет.** KI-617 предлагал
   `LLM_ROUTER_MODEL_MAP` или `data.localModel`: оператор сам выбирает, какой
   локальной моделью заменять `gpt-4o`. В S1 сделан автоматический подбор
   первой совместимой; маппинг остался в планах (в §6 не заводился отдельным
   KI, потому что покрыт KI-630).
5. **Подмена локальной модели видна только в WARN.** `LlmGenerateResult` несёт
   `usage.model` (фактическая модель) и `isLocal`, но UI/история не показывают
   «модель заменена роутером» отдельным признаком. Пользователь видит ответ,
   но не факт подмены. Отдельный KI не заводился: это UX-задача уровня S2+,
   а не дефект (факт фиксируется в span `llm.model_used` и в логе).
6. **Сверка не выполняется при `LLM_ROUTER_ENABLED=false`.** Это осознанно
   (нет подмены — нет сверки), но означает, что «безопасность выбора» зависит
   от флага: включённый роутер строже, выключенный — как раньше. Задокументировано
   в JSDoc класса.
7. **Тест «нет облачного провайдера» остался, но текст ошибки другой.**
   Раньше `resolveCloudRoute` бросал «нет облачного провайдера для fallback»,
   теперь — «нет облачной модели, совместимой…» (провайдера и модели нет —
   это тоже отсутствие совместимой модели). Тест проверяет тип исключения;
   это изменение текста стоит учитывать при разборе логов.
8. **`LlmModelInfo` (список моделей для UI) не получил новых полей.**
   `supportsTools`/`maxTokens` не пробрасываются в `GET /llm/models`, поэтому
   UI не может показать «модель не умеет tools». Это не ошибка S1 (задача
   касалась `ModelInfo` и реестра), но добавление полей в REST-ответ потребует
   правок `LlmModelInfoSchema` и паритет-гейта (`Llm*` вне KI-352, см. KI-627).
9. **Смоук зависит от «чистого» окружения.** `.env` подмешивал реальные ключи
   Yandex, из-за чего фаза 3 нашла совместимую модель и завершилась успешно.
   Пришлось явно занулять чужие ключи; в отчёте это зафиксировано, чтобы
   следующий смоук не повторил ошибку.
10. **В реестре снова появились краткие дубли KI-626..628.** На HEAD было 618
    заголовков при 615 уникальных номерах: после подробных записей S3 шла

    KI-622..625 ранее). Дубли удалены, сводка пересчитана grep'ом (RULES 3.20):

11. **`pnpm lint` — 2 преэкзистующих warning'а** в

12. **Коммитов нет.** Все изменения — в рабочем дереве: 14 изменённых файлов +
    2 untracked (`src/llm/model-capabilities.ts`, `.spec.ts`). Отчёт —

## 7. Обоснование решений

1. **Отдельный модуль `model-capabilities.ts`, а не методы в роутере.**
   Сверка — чистая функция над паспортами: её используют и роутер, и реестр
   (`findCompatibleRoute`), и тесты. В роутере она смешалась бы с логикой
   маршрута и стала бы недоступна для поиска по каталогу.
2. **Нормализация паспорта (`buildModelCapabilities`), а не прямое чтение
   `ModelInfo` в сравнениях.** Поля опциональны (сторонние/env-объявления,
   тесты), и каждое сравнение повторяло бы `?? false`/`?? true`. Нормализация
   один раз в одном месте — единственный способ не разъехаться в трактовке
   отсутствующих значений.
3. **`supportsTools` по умолчанию `true` для текстовых моделей, а не `false`.**
   Инструменты агента передаются промптом, а не нативным tool-calling: любая
   текстовая модель способна вести цикл. `false` по умолчанию отключил бы
   локальный GPU для агента вообще (у LM Studio нет метаданных о tools) —
   это была бы регрессия вместо исправления. Риск эвристики — KI-631.
4. **`requiresTools` — opt-in от вызывающего кода.** Требование tool-calling
   имеет смысл только для агента; для LLM-узла без инструментов оно было бы
   ложным и отсекало бы модели без причины. Флаг задаёт агент, а не паспорт
   модели.
5. **Контекст сравнивается только при известных значениях.** Требовать
   `maxTokens` от env-каталогов нельзя — поля там нет; «неизвестно» не равно
   «не подходит». Иначе все модели из `LMSTUDIO_MODELS` перестали бы
   подходить под любое требование от встроенной модели (у которой контекст
   известен). См. KI-629.
6. **Требования из паспорта исходной модели, а не из узла.** Альтернатива —
   передавать модальности запроса из исполнителя узла — потребовала бы
   правок контракта `LlmGenerateOptions` и всех исполнителей; в S1 выбран
   консервативный вариант «не подменяем модель на более слабую», а точность
   (vision только когда картинки реально есть) вынесена в KI-630.
7. **Fallback: исходная модель пользователя в приоритете.** KI-617 прямо
   предлагал «fallback на исходную облачную модель, если она объявлена
   провайдером». Это же снимает половину проблемы «подменили модель»: при
   `gpt-4o` fallback идёт в `gpt-4o`, а не в `LLM_ROUTER_FALLBACK_MODEL`.
   Модель из env остаётся вторым приоритетом — на случай, если исходная
   локальная (её в облаке нет).
8. **`LlmProviderException` вместо подбора «хоть какой-нибудь» модели.**
   Если совместимых нет, любой вызов заведомо семантически неверен: vision-
   запрос в текстовую модель или agent-шаг в модель без инструментов. Явная
   ошибка с перечнем требований и причин отказа fallback диагностичнее и не
   тратит деньги на заведомо неподходящий upstream.
9. **Подбор первой совместимой облачной модели, а не «первой модели первого
   провайдера».** Порядок провайдеров (`LlmProviderFactory`) остаётся
   приоритетом, но внутри него пропускаются несовместимые модели и
   неконфигурированные провайдеры. Это делает результат детерминированным и
   не зависит от того, что первым объявлено.
10. **WARN при подмене локальной модели, а не debug.** До S1 подмена
    логировалась в debug (в проде не видна). KI-617 требовал «логируй WARN при
    подмене модели» — теперь оператор видит и факт подмены, и требования.
11. **`pickLocalModel` возвращает `null` вместо выброса исключения.** «Нет
    совместимой локальной модели» — не ошибка: это нормальный повод сразу
    уйти в облако, а не падать. Исключение оставлено только для случая, когда
    нет и совместимой облачной модели.
12. **Реестр в тестах роутера — настоящий.** Фейковый объект пришлось бы
    дополнять `getCapabilities`/`findCompatibleRoute`, и рассинхрон с
    реализацией давал бы ложно-зелёные тесты (§ 3.7).
13. **Новые поля не пробрасываются в `GET /llm/models`.** Задача фиксировала
    изменения `ModelInfo` и реестра; REST-ответ и его Zod-зеркало — отдельный
    контракт (LLM-зеркала вне паритет-гейта, KI-627). Добавление полей без
    гейта увеличило бы риск рассинхрона; вынесено в § 5, п. 8.
14. **Смоук — три фазы с перезапуском backend, а не один процесс.** Каталог
    LM Studio и ключи облака читаются фабрикой при старте, поэтому «поменять
    модель у того же процесса» нельзя. Три процесса — три честные
    конфигурации; прогон занимает ~10 с.
15. **Деталь смоука: зануление чужих ключей в env фазы.** Без этого `.env`
    приносил Yandex-ключи, и фаза 3 находила совместимую модель (что
    подтверждает корректность кода, но ломает проверку). Явное зануление —
    единственный способ проверить именно «нет совместимого облака».
16. **Паспорта заполнены для встроенных каталогов, а не для env.**
    Встроенные каталоги — код, который сопровождается вместе с паспортами;
    env-каталоги — операторские данные, и добавлять в них обязательное поле
    `maxTokens` значило бы сломать существующие конфигурации (RULES 4.35:
    строгий разбор). Отсутствие значения трактуется как «неизвестно».
