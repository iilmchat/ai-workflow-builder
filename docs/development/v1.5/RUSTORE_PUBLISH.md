### 2.1. Краткое описание (Short Description)

названии есть аббревиатура (п. 6.4).

**Основной вариант (64 символа из 80):**

<!-- short-description:start -->
Визуальный конструктор AI-сценариев без кода: холст, LLM, агенты

**Запасные варианты:**

| Вариант | Текст | Символов |

### 2.2. Полное описание (Full Description)

**Лимит RuStore:** до 4000 символов; пользователь может свернуть описание до
2000 символов, поэтому первые абзацы должны объяснять суть без прокрутки.

**Текст для копирования (3358 символов из 4000 — запас 642; пересчитано после
S5-B):**

<!-- full-description:start -->
IIChatTools AI Workflow Builder — визуальный конструктор AI-сценариев. Соберите сценарий из узлов на холсте, соедините их и запустите: движок выполнит шаги в нужном порядке, а результат появится в панели результата внизу экрана. Писать код не нужно.

Что умеет конструктор:
- 22 типа узлов: текст, LLM, агент, генерация и обработка медиа (изображения, видео, озвучка, музыка), условия, сравнение, HTTP, веб-поиск, генерация документов, чтение и запись файлов, векторная память, вложенные сценарии, вывод и комментарии.
- Модели на выбор: Anthropic, OpenAI, DeepSeek, Yandex AI Studio, RouterAI, GPTunnel, LM Studio. Модель и лимит токенов задаются в самом узле.
- Агенты: LLM-цикл с инструментами — HTTP, векторный поиск, память. Внешние MCP-серверы подключаются, если администратор включил MCP.
- Медиа: изображения, видео, аудио, музыка; апскейл, удаление фона, lipsync.
- Документы: Markdown или JSON превращается в DOCX или PDF, есть шаблоны .docx с плейсхолдерами.
- Веб-поиск: Tavily, Bing или Brave — источники и готовый текст для следующего узла.
- Надёжность: фоновые запуски в очереди, повторные попытки при ошибках провайдера, отмена запуска, история и сравнение прогонов.
- Бюджет: лимит стоимости запуска, учёт токенов и стоимости в рублях и долларах.
- Команда: организации, роли, приглашения по email, публичные ссылки на сценарий.
- Локальный GPU: если администратор включил LLM Router, запросы сначала идут в LM Studio, а при недоступности — в облако.

Возможности Android-приложения:
- Сканер QR: наведите камеру на QR-код сценария или публичной ссылки — сценарий откроется в приложении. QR-сканер работает на устройствах с Google Play Services.
- Документы: готовый DOCX или PDF скачивается в память устройства и открывается системным просмотрщиком.
- Push-уведомления через RuStore Push: разрешение запрашивается после входа, доставка не зависит от Google Play Services.
- Тот же аккаунт, что в веб-версии: сценарии, история и команда синхронизированы.
- Приложение работает с сервером IIChatTools по HTTPS; отдельный аккаунт не нужен — вход тот же, что в веб-версии.

Для кого:
- Маркетологам: сценарии генерации текстов, изображений и документов без ручной сборки промптов.
- Разработчикам: прототипы AI-пайплайнов, HTTP-шаги, MCP-инструменты, импорт и экспорт сценариев.
- Аналитикам: повторяемые цепочки «поиск → LLM → документ» с историей и стоимостью каждого запуска.
- Командам: общие сценарии с ролями и публичными ссылками для согласования.

Почему удобно:
- Визуальная сборка: узлы и связи вместо кода, отмена, копирование, горячие клавиши.
- Прозрачность: видно, сколько стоит запуск, какие шаги выполнялись и где произошла ошибка.
- Экспорт и импорт: сценарий можно сохранить в файл и перенести на другой сервер.
- Интерфейс на русском и английском языках, светлая и тёмная темы.
- MCP: подключение внешних инструментов через стандартный протокол, если он включён администратором.

Что важно знать:
- Приложение работает с сервером IIChatTools по HTTPS; аккаунт создаётся на этом сервере.
- Полноценно редактировать граф удобнее на большом экране: телефон — для просмотра, запуска и мобильных функций.
- Push-уведомления доступны на устройствах с установленным RuStore.
- QR-сканер работает на устройствах с Google Play Services; на устройствах без GMS кнопка «Сканировать QR» недоступна.
- Версия для iOS пока не выпускается.
<!-- full-description:end -->

**Иконка.** Для карточки — `icon-512x512.png` (512 × 512, фон по всей площади,
без прозрачных краёв). Для установленного приложения нужны mipmap-иконки:
сейчас в `web/android/app/src/main/res/mipmap-*` лежат стандартные из шаблона
Capacitor (B-4) — заменить на брендовые до релизной сборки, иначе иконка в
карточке не совпадёт с иконкой на устройстве.

**Feature Graphic.** Поля для баннера мобильной версии в карточке RuStore
**нет** (на 2026-11-09): баннер требуется только для ТВ-версии, а её в v1.5.0
нет. Поэтому баннер — для промо вокруг карточки (анонс, VK-сообщество, обложка
видео, реклама), а не для загрузки в Console. Версия 1024 × 500 — для площадок,
которые просят такой размер.

**Обязательно убрать с кадров:** строку состояния и навигационную панель

механика (п. 6.6).

**Чего не показывать:** полноэкранный сканер QR (UI Google ML Kit) и шторку
уведомлений Android — это системный UI; DOCX в Word/Google Docs — интерфейс
другого приложения. Push и сканер лучше показать в видео.

### 3.4. Видео (опционально)

Поле «Видео» принимает ссылку на **VK Видео** (`vk.ru`, `vk.com`,
`vkvideo.ru`), ролик публичный, 1–2 минуты, 16:9 или 9:16. Здесь системный UI
допустим: можно показать сканирование QR, скачивание DOCX и пришедший push. Для
«Фонового видео» — отдельный ролик без звука, ключевые кадры в центральных 80 %
и вне нижней трети.

### 4.2. Политика конфиденциальности (нужен URL)

**Требование RuStore (п. 5.1):** приложение, которое собирает или обрабатывает
персональные данные, должно иметь политику конфиденциальности **и предоставлять
доступ к ней** — на русском языке, со ссылкой в карточке приложения и в самом
приложении. Политика должна содержать категории собираемых данных, цели
обработки, сроки хранения, порядок удаления и контакт лица, ответственного за
обработку.

**Что происходит в v1.5.0:** собираются email и пароль (хранится хеш), ID
пользователя и организации, сценарии и их содержимое, сгенерированные
документы и медиа, push-токен устройства. Данные уходят третьим лицам —
провайдерам LLM и медиа, в S3, через SMTP при приглашениях. Отдельного
документа в репозитории **нет** — его нужно подготовить и опубликовать.

**Чек-лист политики:**

- [ ] оператор ПД: юрлицо/ИП, ИНН, адрес, контакт ответственного за обработку;
- [ ] категории данных: email, ID пользователя, содержимое сценариев и файлов,
      сгенерированные медиа, push-токен, технические логи;
- [ ] цели: регистрация и вход, работа сценариев, приглашения в команду,
      уведомления, поддержка;
- [ ] получатели: провайдеры LLM/медиа (перечень), S3-хранилище, SMTP;
- [ ] сроки хранения и порядок удаления (включая удаление аккаунта, § 4.4);
- [ ] трансграничная передача (если провайдеры за пределами РФ) и локализация
      первичной базы — уточнить у юриста;
- [ ] права пользователя: доступ, исправление, удаление, отзыв согласия;
- [ ] дата публикации и порядок изменений;
- [ ] ссылка на политику внутри приложения (экран входа, рядом с согласием —
      § 4.3).

**URL и где его указать.** Отдельного поля «Политика конфиденциальности» в форме
версии на 2026-11-09 нет; п. 5.1 требует доступность политики, поэтому:
опубликовать её на сайте продукта (`https://<домен>/privacy`), указать сайт в
«Способах связи», приложить ссылку в комментарии модератору и дать ссылку в
приложении. Если поле появится в «Настройке публикации» — вставить URL туда.

### 4.3. Согласие на обработку персональных данных

- [ ] В форме регистрации добавить чекбокс «Я принимаю политику
      конфиденциальности и даю согласие на обработку персональных данных» со
      ссылкой на политику. Без активного чекбокса регистрация недоступна.
- [ ] Отдельное согласие на необязательные вещи (например, push) — не
      смешивать с обязательным: разрешение на уведомления запрашивается
      системно и может быть отозвано.
- [ ] Для уже зарегистрированных пользователей — показать экран принятия
      обновлённой политики при следующем входе.

**Сейчас (v1.5.0):** на `LoginPage` есть только email и пароль, ссылки на
политику и чекбокса согласия нет — это B-3. Без доработки отправлять на
модерацию рискованно.

### 4.4. Удаление аккаунта

**Требование RuStore (п. 5.4):** если в приложении можно создать учётную
запись, должна быть возможность удалить её **внутри приложения**, с удалением
или обезличиванием связанных данных. Единственный путь «напишите в
поддержку» не допускается.

- [ ] кнопка «Удалить аккаунт» в настройках/профиле;
- [ ] диалог подтверждения с предупреждением о необратимости;
- [ ] серверная ручка удаления/обезличивания (сейчас в `src/auth` её нет —
      только register/login/refresh/logout/me);
- [ ] удаление сценариев, файлов, медиа и push-токенов пользователя;
- [ ] запись в политике о сроках и порядке удаления.

Это B-3: без ручки и экрана публикация может быть отклонена.

### 4.5. Пользовательский контент (UGC) и публичные ссылки

Приложение позволяет делиться сценарием по публичной ссылке
(`/workflow/share/<token>`) и совместно работать над сценариями. RuStore
(п. 8.3) для UGC-приложений требует правила пользования, модерацию контента,
механизм жалоб и блокировки. В v1.5.0 этих механизмов нет.

Варианты до релиза (решение владельца продукта):

1. Добавить правила пользования и форму жалобы — самый надёжный путь для
   публичного share.
2. Не анонсировать публичные ссылки как ключевую функцию и быть готовым
   обосновать модератору, что ссылка не индексируется и выдаётся только
   владельцем сценария (токен случайный, карточка не публикуется в каталоге).
3. Ограничить share-ссылку до выпуска (например, только для участников
   организации) — потребует кода, но снимает вопрос UGC.

### 4.6. Безопасность данных (декларация разрешений)

Блок **«Безопасность данных пользователя»** в форме версии обязателен:
чувствительные разрешения + категории и типы данных.

**Чувствительные разрешения и что написать в поле «Обоснование»:**

| Разрешение | Что написать в поле «Обоснование» |
|---|---|
| `CAMERA` | Сканирование QR-кодов сценариев. Камера включается только по нажатию кнопки «Сканировать QR»; фото и видео не сохраняются и не передаются |
| `POST_NOTIFICATIONS` | Push-уведомления через RuStore Push. Разрешение запрашивается после входа; отказ не блокирует работу приложения |

`READ_MEDIA_IMAGES`, `READ_EXTERNAL_STORAGE` и `WRITE_EXTERNAL_STORAGE` в
манифесте **не объявлены** (S5-B, KI-663): приложение не открывает галерею и не
сохраняет фото в общий storage, поэтому в блоке «Безопасность данных» их
отмечать не нужно. `CAMERA` и `POST_NOTIFICATIONS` — единственные
чувствительные разрешения; `INTERNET` — обычное.

**Категории и типы данных — отметить:**

| Категория | Тип | Откуда в приложении |
|---|---|---|
| Личная информация | Адрес электронной почты | регистрация, вход, приглашения |
| Личная информация | ID пользователей | `users.id`, `organization_id`, сессии |
| Файлы и документы | Файлы и документы | шаблоны DOCX, генерация и скачивание документов |
| Фото и видео | Видео | только сгенерированные видео (хранение в S3) |
| Аудиофайлы | Аудиозаписи, музыкальные файлы | генерация озвучки/музыки, lipsync |
| Действия в приложении | Другой пользовательский контент | сценарии, промпты, тексты, результаты (изображения — сюда же) |
| Идентификаторы | ID устройства или другие идентификаторы | push-токен устройства (`device_tokens`) |
| Данные о работе приложения | Диагностика | технические логи backend (если Консоль предложит отметить) |

**Третьи лица, которых нужно указать:** провайдеры LLM (Anthropic, OpenAI,
DeepSeek, Yandex AI Studio, RouterAI, GPTunnel, LM Studio), провайдеры медиа
(GPTunnel CreativeLab, Replicate, FAL, OpenAI Images), S3-хранилище, SMTP-сервер
для писем. Перечень должен совпадать с политикой конфиденциальности.

## 5. Инструкция по загрузке (Step-by-Step)

### 5.0. Предусловия (проверить до входа в Консоль)

- [ ] Роль в RuStore Консоли: **Владелец компании** — только он может добавить
      приложение; версии загружают владелец, администратор, релиз-менеджер,
      разработчик.
- [ ] Публичный HTTPS-адрес backend и рабочий аккаунт (B-1 закрыт в S5-B;
      B-3 — удаление аккаунта и согласие на ПД — ещё нет).
- [ ] `vars.VITE_API_BASE` задан (публичный HTTPS-URL backend без `/api`) —
      иначе release-AAB не авторизуется (KI-658, `RUSTORE_SETUP.md`).
- [ ] Собранный AAB: GitHub Actions `Release Mobile (Android)` → артефакт
      30 дней, файл `app-release.aab`; локально —
      `web/android/app/build/outputs/bundle/release/app-release.aab`.
- [ ] Release keystore и пароли (см. `KEYSTORE_SETUP.md`); AAB подписан тем же
      ключом, чей SHA-256 указан в проекте RuStore Push.
- [ ] Project ID и Service Token RuStore Push заведены (`RUSTORE_SETUP.md`),
      `VITE_RUSTORE_PROJECT_ID` и `VITE_API_BASE` попали в сборку.
- [ ] Тексты (§ 1–2), картинки (§ 3), политика (§ 4.2) готовы.
- [ ] Решён вопрос с `versionCode`: публичная версия после альфы должна быть
      **выше** альфа-сборки. Если альфа = `1`, публичную собирать с `2`
      (правится в `web/android/app/build.gradle`, параметра в CI нет).

### 5.1. Добавить приложение

1. Открыть [RuStore Консоль](https://console.rustore.ru/) под VK ID.
2. Вкладка **Приложения** → **Добавить приложение**.
3. Ввести название `AI Workflow Builder` → **Добавить**.
4. Выбрать приложение → **Загрузить версию**.

### 5.2. Загрузить подпись (обязательно для AAB)

AAB нельзя загрузить без подписи: RuStore пересобирает APK и подписывает их
ключом подписи приложения, а сам AAB должен быть подписан ключом загрузки.
Именно отпечаток ключа подписи (не загрузки) должен совпадать с отпечатком в
проекте RuStore Push — иначе установленное приложение не получит push.

1. В форме версии нажать **Загрузить** напротив предупреждения
   **«Подпись не загружена»**.
2. Скачать `pepk.jar` из окна загрузки подписи.
3. Скопировать из Консоли готовую команду запуска PEPK (в ней уникальный
   `encryptionkey`) и подставить путь к release-keystore, alias и каталог
   вывода. Команда запускается там, где лежит `pepk.jar`; в ZIP попадает
   зашифрованный ключ подписи приложения.
4. Экспортировать сертификат ключа загрузки в PEM:
   `keytool -exportcert -alias <alias> -keystore <keystore> -rfc -file uploadcert.pem`.
5. Загрузить ZIP (подпись) и PEM (сертификат) → **Отправить подпись**.

**Про ключи.** В CI AAB подписывается одним release-ключом, поэтому для первого
релиза допустимо использовать его и как ключ подписи приложения (PEPK), и как
ключ загрузки (PEM) — схема простая, а SHA-256 для push-проекта берётся из того
же сертификата. Если позже понадобится отдельный upload key, AAB придётся
подписывать им в CI, а ключ подписи приложения останется только в PEPK-архиве.

Требования: ключ RSA не менее 2048 бит, Java 11+. Подробности —
[«Как загрузить AAB»](https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/upload-aab).

### 5.3. Загрузить AAB

1. В той же форме — **Выберите файл** → `app-release.aab` (до 5 ГБ, имя файла
   уникально, package name `com.iilmchat.workflowbuilder`).
2. **Не покидать страницу во время загрузки** — она прервётся. После загрузки
   идёт фоновая обработка; можно сохранить черновик и уйти.
3. Обработанные файлы хранятся 14 дней — если не отправить на модерацию,
   их удалят.

Проверить в Консоли: `versionCode` = 1 (альфа/первая версия; для публичной
после альфы — 2), `versionName` = 1.5.0, package name.

### 5.4. Заполнить форму версии

1. **Что нового?** — текст из § 1.
2. **Информация о приложении** — название, категория, возрастной рейтинг,
   теги, краткое и полное описание (§ 2), минимальная версия Android
   подтянется из манифеста.
3. **Способы связи** — email, сайт, VK (§ 4.1).
4. **Медиафайлы** — иконка 512 × 512, скриншоты (§ 3); видео — по желанию.
5. **Безопасность данных пользователя** — обоснования разрешений и типы данных
   (§ 4.6).
6. При необходимости — **FAQ** (до 10 пар, вопрос ≤ 120 символов, ответ ≤ 500).
7. **Отправить на модерацию** или **Сохранить как черновик** (черновик один).

### 5.5. Запустить Альфа-тестирование (для проверки push)

Альфа-версия — закрытое тестирование: версия тоже проходит модерацию и
публикуется в мобильном каталоге RuStore, но видна только приглашённым
тестировщикам (по ссылке или в каталоге). Это позволяет проверить push до
публичного релиза.

1. Консоль → **Приложения** → приложение → **Тестирование** →
   **Альфа-тестирование** → **Альфа-версии** → **Загрузить версию**.
2. Проверить предзаполненные данные версии (подтягиваются из публичной версии;
   для первой публикации — заполнить вручную), при необходимости
   отредактировать → **Отправить на модерацию**.
3. Добавить тестировщиков: **Тестирование → Альфа-тестирование →
   Тестировщики → Пригласить тестировщика** — VK ID через запятую, до 2000
   человек. VK ID в RuStore у тестировщика должен совпадать с приглашённым.
4. После модерации Консоль сформирует ссылку на версию; тестировщик
   авторизуется в RuStore и переходит по ней **с мобильного устройства**
   (альфа-версии видны только в мобильном каталоге, не в веб-версии).
5. Проверить на устройстве: вход (backend по HTTPS из `VITE_API_BASE`), QR-скан
   на устройстве с GMS, скачивание DOCX/PDF, разрешение на уведомления.
   Токена push в клиентском логе нет — проверять по записи в `device_tokens`
   (SQL из `RUSTORE_SETUP.md`, шаг 4).
6. Проверить push по событию (S5-B, KI-659): запустить сценарий из приложения и
   дождаться финала. По умолчанию push приходит только на `failed`; для
   `completed` нужен `PUSH_ON_RUN_COMPLETE_SUCCESS=true` на backend. В Logcat —
   `adb logcat | Select-String "RuStore Push"` (ожидаемо
   `RuStore Push: notification received`).
7. Тестовая отправка push: Консоль → **Push-уведомления → Проекты** → проект →
   вкладка **Тестовые уведомления** → вставить push-токен из `device_tokens` →
   отправить. Уведомление должно прийти за несколько секунд.
8. Убедиться, что SHA-256 сертификата, которым подписан установленный APK,
   совпадает с отпечатком в push-проекте: `keytool -list -v -keystore
   <release.keystore> -alias <alias>` (SHA256) либо `apksigner verify
   --print-certs <файл.apk>` — для файла APK, не для установленного приложения.
9. Завершить тестирование: **Альфа-версии** → три точки → **Завершить
   тестирование**. Сборка уйдёт в архив.

Ограничения альфы: одновременно только одна альфа-версия; только бесплатные
приложения на мобильных; на эмуляторе без RuStore push не проверить.

### 5.6. Публикация основной версии

1. В `web/android/app/build.gradle` поднять `versionCode` 1 → 2 (контракт
   RuStore: код публичной версии выше альфа-сборки) и собрать AAB с тем же
   `versionName` 1.5.0.
2. Консоль → приложение → **Загрузить версию** → загрузить новый AAB (подпись
   уже загружена).
3. Проверить и отправить на модерацию.
